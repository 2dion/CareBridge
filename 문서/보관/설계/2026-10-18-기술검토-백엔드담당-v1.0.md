## 새로 찾은 문제: 파일 이름 검사와 코드 폴더

지금 규칙 그대로면 Next.js 코드를 올리는 첫 PR부터 빨간 X가 뜨고, 필수 파일 이름을 바꿀 방법도 없습니다. 10/17에 추가된 "파일 이름 검사"(.github/scripts/check-filenames.py)는 저장소의 모든 파일에 한글·영문·숫자·-·.만 허용합니다. 그런데 Next.js와 Supabase는 이름 규칙 자체가 대괄호·괄호·밑줄을 씁니다.
지금 당장은 문제가 없습니다. 저장소에 아직 코드가 없기 때문입니다. 문제는 개발이 시작돼 코드를 처음 올리는 순간부터입니다. 아래 표는 우리가 만들 파일 이름을 같은 검사 규칙에 미리 넣어 본 결과입니다(10/18, 내 PC에서만 실험). "실패"는 올리면 빨간 X가 뜬다는 뜻이고, 이 이름들은 Next.js·Supabase·GitHub이 정한 것이라 우리가 바꿀 수 없습니다.

| 파일 (예) | 왜 이 이름인가 | 검사 결과 |
| --- | --- | --- |
| web/app/api/records/[id]/route.ts | Next.js의 "주소에 따라 바뀌는 화면"(기록 1건 보기 등)은 [ ] 폴더로만 만듦 | 실패 |
| web/app/(auth)/login/page.tsx | 화면 묶음 폴더는 ( ) | 실패 |
| web/app/_components/... | 주소가 안 되는 폴더는 _ | 실패 |
| supabase/migrations/20261020000000_init.sql | Supabase 도구가 시간_이름.sql로 자동 생성 | 실패 |
| .github/pull_request_template.md | GitHub이 이 이름일 때만 PR 양식으로 인식 | 실패 |
| CLAUDE.md, .claude/settings.json, .github/workflows/ci.yml, web/.env.example | — | 통과 |

제안: 파일 이름 검사는 문서 폴더에만 겁니다. 규칙의 목적(팀원이 웹으로 올리는 문서·자료 정리)은 그대로 지키고, 코드 폴더만 빼는 것입니다.

- 그대로 검사: 문서/, 참고자료/
- 검사 제외: web/, supabase/, .github/. 각 도구가 정한 이름을 따르고, 코드가 깨졌는지는 CI(lint·타입 검사·빌드)가 대신 확인합니다.
- 바꿀 곳: .github/scripts/check-filenames.py에서 검사할 파일을 문서/·참고자료/로 시작하는 것만 고르는 부분 추가, 루트 README "파일 이름 규칙"에 "코드 폴더는 제외" 한 줄. 수정본은 준비되어 있고(저장소에는 아직 안 올림), 코드 파일은 통과하고 문서·참고자료의 틀린 이름은 지금처럼 잡아내는 것까지 시험했습니다(10/18).
- 누가, 언제: 스크립트를 만든 팀장께 부탁드립니다. 코드를 처음 올리기 전에만 바뀌면 됩니다.
지금은 코드 폴더까지 검사해서 코드 PR마다 빨간 X가 뜹니다. 제안대로면 문서 폴더는 지금 규칙을 그대로 지키고, 코드 폴더는 CI가 대신 검사합니다.

## 기술 선택 v1.0 수정 제안

"음성 기록 처리 흐름" 2단계를 "녹음 파일을 Supabase 저장소에 바로 올리고, 서버에는 위치를 보냅니다"로 바꿉니다. "1분 넘는 음성은 나눠 보내기"는 실행 시간이 300초라 필요성이 낮고, 실제 제약은 4.5MB입니다.

기존에는 녹음 파일이 서버를 거쳐서 4.5MB를 넘으면 막힙니다. 변경 후에는 휴대폰이 파일을 Supabase 저장소에 올리고 서버에는 위치만 보내며, 서버가 저장소에서 파일을 꺼내 STT·Claude로 처리합니다.

## AI 공동 작업 개발 환경

팀원 다섯 명이 각자 AI 코딩 도구를 써도 같은 규칙으로 코드를 쓰도록, AI가 먼저 읽는 규칙 파일과 사람이 리뷰한 코드만 합치는 장치를 둡니다. 초안은 모두 준비되어 있고, 저장소에는 아직 올리지 않았습니다.

| 파일 | 하는 일 | 언제 올림 |
| --- | --- | --- |
| CLAUDE.md | AI 코딩 도구가 작업 전에 읽는 팀 공통 규칙 (가장 중요) | 바로 가능 |
| AGENTS.md | 다른 AI 도구(Codex 등)도 CLAUDE.md를 따르게 하는 한 줄 | 바로 가능 |

| .github/workflows/ci.yml | PR마다 lint·타입 검사·빌드 자동 확인 (기존 파일 이름 검사와 따로 돔) | Next.js 뼈대 뒤 |

## 브랜치·PR 규칙 (브랜치 보호를 못 켜서 팀 규칙으로 지킵니다)
1. main에 직접 push하지 않습니다.
2. 작업을 시작할 때마다 main 최신본을 먼저 받고, 기능마다 브랜치를 만듭니다: feat/w2-voice-memo, fix/r2-approve-button, docs/dev-env. 브랜치는 1~2일 안에 PR로 올려 충돌을 줄입니다.
3. 한 PR에는 화면 하나 또는 기능 하나만. PR 양식에 AI 도구 사용 여부와 Issue 번호(예: Closes #3)를 적습니다. Issue 연결은 코디세이 평가의 역할 분담·기여도 증거가 됩니다.
4. 다른 팀원 1명이 리뷰합니다. 화면과 일반 서버 코드(app/api)는 팀원(서버 코드는 백엔드 담당)이, DB 구조·RLS, 키·환경 변수, 배포 설정 변경은 팀장이 리뷰합니다. AI가 쓴 코드도 사람이 읽고 확인합니다.
5. 리뷰는 하루 안에 합니다. 하루가 지나면 채널에서 다시 부릅니다.
6. 자동 검사와 리뷰를 통과한 PR을 main에 합치는(merge) 사람은 팀장(저장소 주인)입니다. Vercel 무료 요금제가 비공개 저장소에서 계정 주인의 커밋만 배포하기 때문이며, 첫 PR에서 실제로 배포되는지 확인합니다.
## API 키 관리 규칙

키 담당자: ○○○
코디세이 키 사용이 정해지면 아래 규칙을 적용합니다. 코디세이 API 키는 팀 전체가 함께 사용하는 한정된 자원입니다. 키가 유출되거나 한도가 소진되면 팀 전체의 개발과 서비스 이용이 중단될 수 있습니다. 모든 팀원은 아래 규칙을 반드시 준수합니다.
1. API 키는 담당자 1명만 보관합니다.
   - API 키는 지정된 키 담당자 1명만 보관하고 관리합니다.
   - 다른 팀원에게는 어떤 방법으로도 키를 전달하지 않습니다. (1:1 메시지, 단체 채팅, 링크, 구두 전달 등 모두 금지)
   - 팀원은 키가 아닌 테스트 결과와 사용 방법만 공유받습니다.
2. API 키를 외부에 노출하지 않습니다.
   - 디스코드, 카카오톡, 코드, 문서, 스크린샷, AI 채팅창 등에 API 키를 입력하거나 게시하지 않습니다.
   - API 키를 소스 코드에 직접 작성하거나 공개 저장소에 올리지 않습니다.
   - API 키가 포함된 로그, 오류 메시지, 네트워크 응답 등을 외부에 공유하지 않습니다.
   - 서버 코드에서 요청 헤더, 환경 변수, 설정 객체 전체를 로그로 출력하지 않습니다. (Authorization 헤더 등에 키가 포함될 수 있음)
   - GitHub 무료 비공개 저장소에서는 Secret Scanning을 쓸 수 없으므로, 커밋 전과 리뷰에서 키가 들어 있지 않은지 확인합니다.
3. API 키는 지정된 위치에만 저장합니다.
   - 로컬 개발: 키 담당자 PC의 web/.env.local
   - 배포 환경: 키 담당자가 직접 설정하는 Vercel 프로젝트의 환경 변수
   - Vercel 환경 변수는 Production 환경에만 등록하고, Preview·Development 환경에는 등록하지 않습니다.
   - Vercel 환경 변수 등록 시 Sensitive 옵션을 켜서 등록 후에는 누구도 값을 조회할 수 없게 합니다.
   - .env.local은 .gitignore에 등록하고 Git 추적 대상에 포함되지 않았는지 확인합니다.
   - .gitignore는 파일을 암호화하거나 유출을 방지하는 보안 장치가 아니므로 별도 주의가 필요합니다.
   - 실제 키가 아닌 환경 변수 이름과 예시 값만 포함한 .env.example을 공유합니다.
   - API 키는 서버 측에서만 사용하며, NEXT_PUBLIC_ 등 브라우저에 공개되는 환경 변수에 저장하지 않습니다.
4. 일반 개발은 API 키 없이 진행합니다.
   - 키가 없는 팀원은 저장해 둔 테스트용 응답(Mock 데이터)을 사용해 개발하고 테스트합니다.
   - Mock 데이터는 키 담당자가 개발 초기에 실제 응답을 받아 정상 응답, 오류 응답, 타임아웃 등 주요 경우별로 만들어 공유합니다. API 응답 형식이 바뀌면 함께 갱신합니다.
   - 실제 연동 테스트 결과와 오류 내용은 키가 포함되지 않은 형태로 팀에 공유합니다.
   - 실제 API 호출 확인은 키 담당자가 관리하는 Production 배포본에서만 진행합니다.
   - 팀원도 배포본에서 기능을 확인할 수 있으나, 같은 요청을 반복하지 않고 필요한 확인만 합니다. 반복 테스트는 Mock 데이터로 진행합니다.
5. API 사용 한도를 아낍니다.
   - 동일한 음성이나 동일한 요청을 불필요하게 반복 전송하지 않습니다.
   - 반복 테스트는 저장된 테스트용 응답을 사용합니다.
   - 중복 클릭, 불필요한 자동 재시도, 무제한 API 호출이 발생하지 않도록 합니다.
   - 다음 장치를 반드시 적용합니다: 요청 횟수 제한, 중복 요청 방지(처리 중 버튼 비활성화), 타임아웃.
   - Vercel 서버리스 환경에서는 메모리 기반 횟수 제한이 제대로 동작하지 않으므로, 외부 저장소(예: Upstash Redis)를 사용해 구현합니다. 담당: ○○○ / 기한: ○○○
   - 키 담당자는 API 사용량과 잔여 한도를 주기적으로 확인하고 팀에 공유합니다.
6. API 키와 배포 환경의 접근 권한을 최소화합니다.
   - 배포본은 외부에 공개하지 않습니다. Vercel 인증으로 Production까지 보호합니다(비밀번호 보호는 무료 요금제에서 불가). 팀원 접속 가능 여부는 키 담당자가 첫 배포 때 확인합니다.
   - Vercel 프로젝트 및 관련 계정의 접근 권한은 필요한 사람에게만 부여합니다.
   - main 브랜치 보호를 켤 수 없으므로, 브랜치·PR 규칙(리뷰 후 팀장이 합치기)으로 대신합니다. (Production 배포에 키가 주입되므로, 검토되지 않은 코드가 키에 접근하지 못하게 하기 위함)
   - 키를 사용하지 않는 팀원에게는 API 키가 없어도 개발할 수 있는 환경을 제공합니다.
   - 키 담당자는 현재 Vercel 요금제와 팀원 커밋이 정상 배포되는지 확인합니다. (무료 플랜은 팀 협업에 제약이 있을 수 있음)
7. API 키 유출이 의심되면 즉시 대응합니다.
   - 키가 코드, 저장소, 채팅, 로그 등에 노출되었거나 비정상적인 사용량 증가가 발견되면 즉시 키 담당자에게 알립니다.
   - 키 담당자는 기존 키를 즉시 폐기하고 새 키를 발급받습니다.
   - 새 키는 키 담당자만 보관하고, 로컬 환경 변수와 Vercel 설정을 갱신한 뒤 재배포합니다.
   - 갱신 후 정상 작동 여부를 확인하고, 기존 키의 사용량과 관련 로그를 점검합니다.
   - 유출된 키를 코드나 문서에서 삭제하는 것만으로는 대응이 완료되지 않습니다. 반드시 기존 키를 무효화해야 합니다. (Git 기록에도 남아 있기 때문)
팀원은 키 없이 Mock 데이터로 만들고 PR을 올립니다. 자동 검사와 리뷰를 통과한 코드만 main에 합쳐져 배포되고, 실제 AI 호출은 키 담당자가 배포본에서 확인해 결과만 공유합니다.
