# (기획 담당) 구현 명세서

Oct 6, 2026 · @EUN GO

## 0. 이 문서를 읽는 AI·개발자가 지킬 규칙

이 문서는 코딩 AI(Claude Code, Cursor 등)와 개발자가 그대로 구현할 수 있도록 쓴 명세서입니다. 작업을 시작하기 전에 이 문서 전체를 읽고, 아래 규칙을 따르세요.

1. **범위 밖 기능을 만들지 마세요.** 1장 '구현 범위'에 없는 기능은 요청이 있어도 구현하지 말고, 필요하면 Issue로 제안만 합니다.
2. **2장 필수 규칙은 어떤 상황에서도 우선합니다.** 기능 구현과 충돌하면 필수 규칙을 지키고, 충돌 내용을 Issue로 남깁니다.
3. **14장 미결정 사항은 임의로 정하지 마세요.** 기본값이 적힌 항목만 기본값으로 구현하고, 나머지는 멈추고 질문합니다.
4. **가상 데이터만 씁니다.** 실제 사람의 이름·연락처·건강 정보를 코드, 테스트, 로그, 프롬프트 예시에 넣지 않습니다.
5. **작업 단위 = GitHub Issue 1개.** 커밋 메시지에 Issue 번호를 넣고, PR에는 해당 기능의 수용 기준(4장) 확인 결과를 적습니다.
6. **테스트 없는 검증 로직은 완료가 아닙니다.** 9장 검증 규칙은 규칙마다 단위 테스트가 있어야 합니다.
7. **화면 문구는 한국어가 기본입니다.** 요양보호사 화면은 한국어와 베트남어를 함께 표시합니다(문구 파일로 분리).

용어 표기: 요양보호사 = caregiver, 담당자 = reviewer, 어르신(수급자) = resident, 관찰 메모 = note, 기록지 초안 = draft.

## 1. 제품 요약과 구현 범위

케어브릿지는 요양보호사가 베트남어로 쓴 관찰 메모를 받아, 칸별 근거가 붙은 한국어 시설급여 기록지 초안을 만들고, 요양보호사 확인과 담당자 승인을 거쳐 저장하는 웹 서비스입니다.

| 구분 | ID | 내용 |
| --- | --- | --- |
| 필수 | F1 | 메모 → 기록지 초안 생성 |
| 필수 | F2 | 칸별 근거 표시, 미기재(missing), 확인 필요(needs\_confirmation) 상태 |
| 필수 | F3 | 요양보호사 확인: 초안의 베트남어 설명(역번역), 확인 요청 답변, 제출 |
| 필수 | F4 | 담당자 검토: 수정, 승인, 반려, 승인 이력 |
| 필수 | F5 | 가명처리: 외부 AI 호출 전 식별정보 치환, 응답 후 기관 내부에서 복원 |
| 선택 | S1 | 응급 보고 문장(템플릿 기반). 14장 결정 전에는 만들지 않음 |
| 선택 | S2 | 음성 입력(STT). 14장 결정 전에는 만들지 않음 |

**고정 조건**

- 입력 언어: 베트남어(vi). 한국어가 섞인 메모도 처리해야 함. 다른 언어는 감지되면 "지원하지 않는 언어" 오류
- 출력 서식: 시설급여 기록지 1종(7장 스키마)
- 대상 기기: 요양보호사는 휴대폰 브라우저(폭 360px 이상), 담당자는 PC 브라우저(폭 1280px 기준)
- 모든 데이터는 가상 기관·가상 어르신·가상 직원(시드 데이터)

**구현하지 않는 것**: 사투리 지원, 인수인계 요약, 한국어 학습, 다국어, 재가 기록지, 외부 시스템(건보공단·ERP) 연동, 네이티브 앱, 결제, 알림 푸시, 회원가입(시드 계정만 사용).

## 2. 필수 규칙

아래 규칙은 기능보다 우선합니다. 근거는 요양보호사 양성 표준교재 9장의 기록 원칙(사실 그대로, 구체적으로, 외부 반출 금지)과 개인정보보호법입니다. 규칙마다 코드로 강제하고 테스트로 확인합니다.

| ID | 규칙 | 구현 방법 |
| --- | --- | --- |
| R1 | 근거 없는 값 금지 | status가 filled인 칸은 evidence가 1개 이상이고, 각 evidence.quote는 가명처리된 원문에 그대로 있어야 함(V1 검사). 없으면 needs\_confirmation으로 강등 |
| R2 | 숫자는 원문에서만 | 값에 들어간 수량·횟수·시간·측정치는 원문에 있는 숫자이거나 허용 변환표(9장)의 변환이어야 함(V2 검사) |
| R3 | 추정·기본값 금지 | 원문에 없는 칸은 value=null, status=missing. "특이사항 없음", "정상" 같은 기본 문구로 채우지 않음 |
| R4 | 애매한 표현은 확인 요청 | 근거 문장에 애매어("많이", "조금", "nhiều" 등, 9장 목록)가 있고 칸이 수량형이면 needs\_confirmation + 질문 생성(V3 검사) |
| R5 | 외부 전송 전 가명처리 | 외부 AI를 부르는 함수는 가명처리 결과 타입만 입력으로 받음. 문자열을 직접 넘기면 컴파일/런타임 오류. 전송 직전 잔여 식별정보 재검사(V6) |
| R6 | 승인 전에는 확정 아님 | AI 응답은 항상 draft로만 저장. approved로 바꾸는 API는 reviewer 권한만 호출 가능 |
| R7 | AI 생성 표시 | 승인 전 모든 초안 화면에 "AI가 만든 초안" 배지. 승인 기록에도 ai\_generated=true와 승인자·시각 저장 |
| R8 | 로그에 본문 금지 | 애플리케이션 로그·에러 리포트에 메모 본문·이름·AI 응답 본문을 남기지 않음. ID와 길이, 상태만 기록 |
| R9 | 스키마 불통과 저장 금지 | LLM 응답이 7장 JSON 스키마를 통과하지 못하면 1회 재시도, 실패 시 draft.status=error로 두고 사용자에게 다시 시도 버튼 표시 |
| R10 | 응급 문장은 자유 생성 금지 | S1을 만들 경우 LLM은 템플릿 선택과 칸 채우기만 하고, 문장을 새로 쓰지 않음 |

## 3. 사용자 역할과 권한

역할은 세 가지이고, 한 계정은 한 역할만 갖습니다. 모든 데이터는 기관(facility) 단위로 분리되며, 다른 기관 데이터는 조회되지 않아야 합니다.

| 권한 | caregiver | reviewer | admin |
| --- | --- | --- | --- |
| 담당 어르신 목록 보기 | 배정된 어르신만 | 기관 전체 | 기관 전체 |
| 메모 작성·초안 생성 | 가능 | 불가 | 불가 |
| 내 초안 확인·제출 | 가능(본인 것만) | 불가 | 불가 |
| 제출된 초안 검토·수정·승인·반려 | 불가 | 가능 | 불가 |
| 승인 기록 조회·PDF 내보내기 | 본인 작성 건만 조회 | 가능 | 가능 |
| 어르신·직원 등록, 배정 | 불가 | 불가 | 가능 |
| 감사 로그 조회 | 불가 | 불가 | 가능 |

- 로그인: 시드 계정 + 비밀번호. 회원가입·비밀번호 찾기는 만들지 않음
- 시드: 기관 1곳, admin 1명, reviewer 2명, caregiver 4명(베트남어 사용자), 가상 어르신 12명
- 권한 검사는 서버 API에서 합니다. 화면에서 버튼을 숨기는 것만으로는 부족합니다.

admin의 등록·배정·감사 로그 조회는 이번에 화면과 API를 만들지 않고, 시드 스크립트와 DB 직접 조회로 대신합니다. 위 표는 권한 설계 기준입니다.

## 4. 기능 요구사항과 수용 기준

각 기능은 아래 수용 기준(AC)을 모두 만족해야 완료입니다. QA는 AC를 그대로 테스트 케이스로 씁니다.

### F1. 메모 → 기록지 초안

요양보호사가 어르신을 고르고 메모를 제출하면, 8장 파이프라인을 거쳐 7장 스키마의 초안이 만들어집니다.

- AC1-1: 메모는 1\~1,000자. 빈 메모나 1,000자 초과는 제출 버튼 비활성 + 안내 문구. API로 들어오면 각각 NOTE\_EMPTY, NOTE\_TOO\_LONG
- AC1-2: 관찰 날짜·시간은 기본값이 현재 시각이고 수정 가능. 초안의 날짜·시간·기록자는 이 입력과 로그인 정보에서 채우며 AI가 만들지 않음
- AC1-3: 제출 즉시 진행 상태("초안을 만드는 중")를 표시하고, 초안은 15초 안(중앙값)에 나온다. 전체 처리가 50초를 넘으면 error로 전환
- AC1-4: 베트남어·한국어가 아닌 메모는 "지원하지 않는 언어" 오류, 초안 미생성
- AC1-5: AI 호출 실패·스키마 불통과 시 R9대로 처리하고, 작성한 메모는 사라지지 않음

### F2. 근거·미기재·확인 필요 표시

- AC2-1: 칸마다 상태 3종(filled / missing / needs\_confirmation)을 색과 글자로 함께 표시(색만으로 구분 금지)
- AC2-2: filled 칸을 누르면 원문에서 근거 부분이 강조 표시됨
- AC2-3: needs\_confirmation 칸에는 한국어·베트남어 질문이 표시됨(예: "물을 몇 컵 드셨나요?")
- AC2-4: 9장 검증에서 강등된 칸은 강등 사유를 함께 표시

### F3. 요양보호사 확인·제출

- AC3-1: 초안 화면에 칸별 베트남어 설명(역번역)을 한국어 값 아래에 표시
- AC3-2: 확인 요청에 답하면(베트남어/한국어 짧은 답) 해당 칸만 다시 처리하고, 답은 원문에 추가 근거로 저장
- AC3-3: needs\_confirmation이 남아 있어도 제출은 가능하되, 제출 전 "확인되지 않은 칸 N개" 경고 표시
- AC3-4: 요양보호사는 값을 직접 고치지 못하고, 메모 추가·답변으로만 바꾼다(기록은 원문 근거에서만 나오게)
- AC3-5: 제출하면 draft.status = submitted

* AC3-6: 반려된 초안(returned)은 ③ 화면 상단에 반려 사유를 보여 주고, 답변이나 메모를 더한 뒤 다시 제출하면 submitted로 돌아감. 추가 메모는 POST /notes로 저장하고, 이어 붙인 원문 전체로 초안을 다시 만든 뒤 반려 시점과 달라진 칸을 '변경됨'으로 표시한다. 담당자가 반려 전에 고친 칸(edited\_by\_reviewer=true)은 덮어쓰지 않는다

### F4. 담당자 검토·승인

- AC4-1: 승인 대기 목록은 needs\_confirmation 칸 수 내림차순, 같으면 제출 시각 오름차순
- AC4-2: 검토 화면은 왼쪽 원문(실명 복원 + 한국어 참고 번역), 오른쪽 기록지 초안
- AC4-3: 담당자는 칸 값을 수정할 수 있고, 수정한 칸은 edited\_by\_reviewer=true로 표시·저장(수정 전 값 보존)
- AC4-4: needs\_confirmation 칸이 하나라도 남아 있으면 승인 불가. 담당자가 값을 넣거나 'missing으로 확정'을 눌러야 함
- AC4-5: 승인 시 approved\_by, approved\_at 저장 / 반려 시 사유(필수, 200자 이내)와 함께 요양보호사에게 되돌림(status = returned)
- AC4-6: 승인된 기록은 수정 불가. 어르신별 이력 화면에서 PDF로 내보낼 수 있음

* AC4-7: reviewer가 ⑤ 화면을 처음 열면 review\_opened\_at을 저장하고, 승인 시각과의 차이를 '담당자 확인 시간' 지표로 쓴다
* AC4-8: 'missing으로 확정'은 PATCH /fields/:key 에 status=missing, value=null을 보내는 것으로 처리

### F5. 가명처리

- AC5-1: 외부 AI로 나가는 요청 본문에 기관에 등록된 어르신·직원 이름, 전화번호, 호실 번호가 하나도 없음(테스트로 자동 확인)
- AC5-2: 같은 초안 안에서 같은 사람은 항상 같은 토큰(예: \[R1\])
- AC5-3: 화면에는 토큰이 아니라 실명으로 보임
- AC5-4: 가명처리 후 잔여 식별정보가 감지되면 외부 호출을 막고 사용자에게 "이름·연락처를 빼고 적어 주세요" 안내

### S1·S2 (결정 전에는 구현 금지)

- S1 응급 보고: 상황 유형 3\~5개(낙상, 의식 변화, 호흡 곤란, 발열, 혈당 이상)별 한국어 템플릿. AI는 유형 선택과 칸 채우기만(R10). 템플릿 문구는 기획 담당이 간호 자문 후 제공
- S2 음성 입력: 녹음 → STT → 텍스트 메모 편집창에 넣기. 사용자가 텍스트를 확인한 뒤 F1로 넘김. 음성 파일은 저장하지 않음

## 5. 화면 명세

화면은 7개입니다. 모든 화면은 로딩·빈 상태·오류 상태를 갖고, 요양보호사 화면은 한국어와 베트남어를 함께 표시합니다.

| 경로 | 화면 | 역할 | 구성 요소 | 주요 동작 |
| --- | --- | --- | --- | --- |
| /login | 로그인 | 전체 | 아이디, 비밀번호, 로그인 버튼 | 역할별 첫 화면으로 이동 |
| /c/residents | ① 어르신 선택 | caregiver | 배정 어르신 카드(이름, 호실, 오늘 제출 여부), 반려된 초안 알림 | 카드 선택 → ② |
| /c/notes/new?resident=:id | ② 메모 입력 | caregiver | 어르신 이름, 관찰 일시, 메모 입력창(글자 수 표시), 예시 문장, 초안 만들기 버튼 | 제출 → 로딩 → ③ |
| /c/drafts/:id | ③ 초안 확인 | caregiver | "AI가 만든 초안" 배지, 칸 목록(한국어 값 + 베트남어 설명 + 상태), 확인 질문 답변창, 반려 사유(반려된 경우), 제출 버튼 | 답변 → 칸 재처리, 제출 |
| /r/queue | ④ 승인 대기 목록 | reviewer | 표(어르신, 작성자, 제출 시각, 확인 필요 칸 수, 미기재 칸 수) | 행 선택 → ⑤ |
| /r/drafts/:id | ⑤ 기록 검토 | reviewer | 왼쪽: 원문 + 근거 강조 / 오른쪽: 칸별 값·상태·수정창 / 하단: 승인, 반려(사유) | 칸 선택 시 근거 강조, 승인·반려 |
| /r/residents/:id/records | ⑥ 어르신별 기록 이력 | reviewer, admin | 날짜별 승인 기록 목록, 기록 상세, PDF 내보내기 | PDF 다운로드 |

**화면 공통 규칙**

- 요양보호사 화면: 본문 글자 16px 이상, 터치 영역 48px 이상, 한 화면에 주요 버튼 1개
- 상태 표시: filled = 기본, missing = 회색 + "미기재", needs\_confirmation = 주황 + "확인 필요" (글자 필수)
- 로딩 중에는 단계 문구를 보여 줌: "개인정보 가리는 중 → 초안 만드는 중 → 검사하는 중"
- 오류 문구는 사용자가 할 일을 말함(예: "다시 시도해 주세요. 작성한 메모는 저장되어 있습니다.")
- 문구는 locales/ko.json, locales/vi.json으로 분리. 베트남어 문구는 원어민 검수 전까지 \[검수 전\] 표시

### 화면 와이어프레임

배치와 정보 순서를 정하는 저충실도 그림입니다. 색·글꼴은 프론트엔드 담당이 정하되, 요소의 순서와 있고 없음은 그림을 따릅니다. ④은 표 하나, ⑥은 날짜별 목록 하나라 위 화면 명세 표로 대신합니다.

## 7. 기록지 초안 JSON 스키마

초안은 칸(field) 목록이고, 모든 칸은 같은 모양의 객체입니다. 아래 칸 목록은 임시안이며, 법정 서식(노인장기요양보험법 시행규칙 별지 제16호 장기요양급여제공기록지(시설급여)) 원문과 대조해 기획 담당이 확정합니다(14장 OPEN-01). 칸 목록은 코드에 하드코딩하지 말고 config/form\_facility\_v1.json 에서 읽습니다.

| key | 표시 이름 | 타입 | 허용값·단위 |
| --- | --- | --- | --- |
| meal\_type | 식사 종류 | enum | 일반식, 죽, 유동식, 경관식 |
| meal\_breakfast | 아침 섭취량 | enum | 전량, 3/4, 1/2, 1/4, 거부 |
| meal\_lunch | 점심 섭취량 | enum | 위와 같음 |
| meal\_dinner | 저녁 섭취량 | enum | 위와 같음 |
| water\_intake | 수분 섭취 | number | ml 또는 컵(unit 필드에 명시) |
| hygiene\_oral\_face | 세면·구강청결 | boolean | 실시 여부 |
| bathing | 목욕 | boolean | 실시 여부 |
| position\_change\_count | 체위변경 | integer | 횟수 |
| mobility\_assist | 이동 도움 | boolean | 실시 여부 |
| urine\_count | 소변 | integer | 횟수 |
| stool\_count | 대변 | integer | 횟수 |
| diaper\_change\_count | 기저귀 교환 | integer | 횟수 |
| blood\_pressure | 혈압 | string | "수축/이완" mmHg |
| body\_temperature | 체온 | number | ℃ |
| blood\_glucose | 혈당 | number | mg/dL |
| cognitive\_emotional | 인지·정서 지원 | text | 한국어 문장 |
| special\_notes | 특이사항(상태 변화와 조치) | text | 한국어 문장. 육하원칙 순서로 |

**칸 객체와 초안 전체 구조**

```json
{
  "form_type": "facility_v1",
  "source_lang": "vi",
  "fields": [
    {
      "key": "meal_lunch",
      "value": "1/2",
      "unit": null,
      "status": "filled",
      "evidence": [{ "note_seq": 1, "quote": "ăn trưa được một nửa" }],
      "explanation_vi": "Bữa trưa: ăn được 1/2",
      "question_ko": null,
      "question_vi": null,
      "downgrade_reason": null,
      "edited_by_reviewer": false
    },
    {
      "key": "stool_count",
      "value": null,
      "unit": null,
      "status": "missing",
      "evidence": [],
      "explanation_vi": "Không có trong ghi chú",
      "question_ko": null,
      "question_vi": null,
      "downgrade_reason": null,
      "edited_by_reviewer": false
    }
  ]
}
```

**규칙**

- status = filled → value ≠ null, evidence 1개 이상 / missing → value = null, evidence = \[\] / needs\_confirmation → question\_ko와 question\_vi 필수
- evidence.quote는 원문(가명처리본)에서 그대로 복사한 부분 문자열. 번역문이나 요약 금지
- 모든 key는 칸 목록에 있는 key를 빠짐없이 한 번씩 포함(없으면 missing으로)
- text 타입 칸의 문장은 evidence에 있는 사실만 담고, 추측·판단 표현("\~인 것 같음")을 쓰지 않음
- 날짜·시간·기록자는 스키마 밖(draft 테이블)에서 관리. AI 출력에 포함하지 않음

* explanation\_vi는 P3가 아니라 P5가 채운다. P3 출력에서는 null이며, 위 예시는 P5까지 끝난 모양이다
* payload는 토큰(\[R1\] 등)이 든 상태로 저장하고, 실명 복원은 응답을 만들 때(P6)만 한다

## 8. AI 처리 파이프라인

메모 하나는 7단계를 거쳐 초안이 됩니다. 외부 AI를 부르는 단계는 P3과 P5 두 곳뿐이고, 나머지는 서버 코드입니다. 모델 이름과 프롬프트는 설정 파일에 두고 draft.model\_name, draft.prompt\_version에 기록합니다.

| 단계 | 이름 | 입력 | 출력 | 실패 시 |
| --- | --- | --- | --- | --- |
| P0 | 입력 정리·언어 확인 | 메모 문자열 | 정리된 문자열(유니코드 NFC, 공백 정리), lang | vi·ko 외 언어 → AC1-4 오류 |
| P1 | 가명처리 | 정리된 메모, 기관 명단 | text\_pseudo, 토큰 목록 | 잔여 식별정보 → AC5-4 |
| P2 | 용어집 찾기 | text\_pseudo | 관련 용어 최대 20개 | 없으면 빈 목록으로 계속 |
| P3 | 칸 채우기(LLM) | text\_pseudo, 칸 목록, 용어 | 7장 스키마 JSON(explanation\_vi 제외) | R9: 1회 재시도 후 error |
| P4 | 검사(코드) | P3 출력, text\_pseudo | 강등이 반영된 JSON | 항상 통과(강등만 함) |
| P5 | 모국어 설명(LLM) | 칸 표시 이름 + 한국어 값만 | 칸별 explanation\_vi | 설명없이 표시 + "설명을 불러오지 못했습니다" |
| P6 | 표시용 복원 | 토큰이 든 문자열, 토큰 표 | 실명이 든 문자열 | 토큰 그대로 표시 |

**P1 가명처리 세부**

1. 기관 명단 매칭: 해당 기관의 어르신·직원 이름(성+이름, 이름만, 호칭 결합 "bà X", "ông X", "X 할머니")을 긴 것부터 치환. 어르신 \[R1\], \[R2\]… / 직원 \[S1\], \[S2\]…
2. 정규식: 전화번호 → \[PHONE\], 호실("305호", "phòng 305") → \[ROOM\], 주민등록번호 형태 → \[ID\]
3. 선택된 어르신은 이름이 메모에 없어도 항상 \[R1\]으로 지칭(프롬프트에 "대상자는 \[R1\]"로 만 전달)
4. 잔여 검사: 1–2 후에도 명단 이름·숫자 패턴이 남아 있으면 차단. 외부 AI로 잔여 검사를 하지 않음(R5)

- 이름 비교는 대소문자를 무시하고, 베트남어 성조 부호를 뺀 형태로도 한 번 더 비교한다(너무 많이 가리는 쪽이 안전).
- 성만 쓴 호칭(예: "김 할머니")은 \[PERSON\]으로 가린다.
- 한계: 명단에 없는 사람 이름은 자동으로 찾지 못한다. ② 화면에 "다른 사람의 이름·연락처는 적지 마세요" 안내를 두고, 성과보고서에 알려진 한계로 적는다.
- 호출 제한: P3·P5 각 호출 20초 타임아웃, 파이프라인 전체 50초 초과 시 error.

**P2 용어집**: data/glossary\_vi\_ko.json. 항목 = {vi, ko, field\_hint, note}. 단순 부분 문자열·변형 매칭으로 충분하며 벡터 DB는 쓰지 않음. 용어집 내용은 기획·자료 담당이 공급.

**P3 프롬프트 (prompt\_version: draft-v1)**

호출 설정: temperature 0, 구조화 출력(JSON 스키마 강제 또는 도구 호출 형식). 아래는 시스템 프롬프트 초안이며 테스트 결과로 고칩니다.

```text
너는 노인요양시설의 급여제공기록지 초안을 작성하는 도구다.
입력은 요양보호사가 베트남어(한국어가 섞일 수 있음)로 쓴 관찰 메모다.
메모 속 [R1]은 기록 대상 어르신, [S1] 등은 직원, [PHONE]·[ROOM]은 가려진 정보다.

규칙:
1. 칸 목록의 모든 key를 한 번씩 출력한다.
2. 메모에 직접 적힌 내용만 기입한다. 추측하거나 일반적인 값을 넣지 않는다.
3. 메모에 없는 칸은 value=null, status="missing".
4. 값을 넣었다면 evidence.quote에 메모의 해당 부분을 한 글자도 바꾸지 말고 그대로 복사한다.
5. 수량·횟수가 애매하면(예: nhiều, ít, 많이) status="needs_confirmation"으로 하고,
   요양보호사에게 물을 짧은 질문을 question_ko와 question_vi에 쓴다.
6. 값은 한국어 공식 요양 용어로 쓴다. 용어집이 있으면 용어집 표현을 우선한다.
7. enum 칸은 허용값 중 하나만 쓴다. 맞는 값이 없으면 needs_confirmation.
8. text 칸은 사실만 간결하게, 언제·무엇을·어떻게·왜 순서로 쓴다. "~인 듯함" 같은 추측 표현을 쓰지 않는다.
9. [R1] 등 토큰은 그대로 두고 실명을 새로 만들지 않는다.
```

사용자 메시지: 칸 목록(key, 표시 이름, 타입, 허용값) + 용어집 항목 + `<note>` 태그로 감싼 text\_pseudo.

**P5 모국어 설명**: 원문을 넣지 않고 한국어 값만 베트남어로 설명하게 합니다(진짜 역번역). 그래야 요양보호사가 한국어 값이 자기 뜻과 다른지 알아차릴 수 있습니다. missing 칸은 고정 문구 "Không có trong ghi chú"를 쓰고 AI를 부르지 않습니다.

**확인 답변 처리(AC3-2)**: 답변을 note(kind=answer, field\_key)로 저장 → P1 → P3를 해당 칸만 대상으로 재실행 → P4 → P5. 다른 칸은 바꾸지 않습니다. 예외로 반려된 초안의 추가 메모(kind=addition, AC3-6)는 어느 칸에 들어갈지 미리 알 수 없으므로, 반려 시점 초안을 payload\_at\_return에 보관한 뒤 이어 붙인 원문 전체로 P1\~P5를 다시 실행하고, 달라진 칸을 표시합니다. edited\_by\_reviewer=true인 칸은 담당자 값을 유지합니다.

## 9. 검증 규칙

P4는 AI 출력을 믿지 않고 코드로 다시 검사합니다. 검사는 값을 고치지 않고 상태를 낮추기만(강등) 하며, 강등 사유를 downgrade\_reason에 남깁니다. 규칙마다 단위 테스트 필수입니다.

| ID | 검사 | 실패 시 |
| --- | --- | --- |
| V1 | evidence.quote가 text\_pseudo에 있는가(공백·대소문자 정규화 후 부분 문자열 일치) | filled → needs\_confirmation, "근거를 원문에서 찾지 못함" |
| V2 | 값(text 칸 포함)에 든 모든 숫자가 근거 문장의 숫자이거나 허용 변환표에 있는가 | needs\_confirmation, "숫자 불일치" |
| V3 | 근거 문장에 애매어가 있고 칸이 수량형(number·integer·섭취량 enum)인가 | needs\_confirmation + 기본 질문 문구 |
| V4 | enum 값이 허용값 안에 있는가, number가 범위 안인가(체온 34\~42, 혈당 20\~600, 횟수 0\~30, 혈압 수축기 60\~250·이완기 30\~150) | needs\_confirmation, "허용 범위 밖" |
| V5 | 스키마 모양: 모든 key 한 번씩, status별 필수값 | 누락 key는 missing으로 추가, 중복 key는 R9 재시도 |
| V6 | text 칸과 모든 값에 명단 실명·전화번호 패턴이 없는가 | 해당 부분을 토큰으로 치환 + 감사 로그 |

**허용 변환표 (V2)** — config/number\_map.json

| 원문 표현 | 변환 값 |
| --- | --- |
| một nửa, nửa, 반, 절반 | 1/2 |
| hết, ăn hết, 다, 전부 | 전량 |
| một phần tư, 1/4 | 1/4 |
| ba phần tư, 3/4 | 3/4 |
| không ăn, từ chối, 안 드심, 거부 | 거부 |
| một, hai, ba … mười / 한·두·세 … 열 | 1\~10 |

**애매어 목록 (V3)** — config/vague\_terms.json: nhiều, ít, một chút, khá, hơi, khoảng, 많이, 조금, 약간, 대충, 좀.

두 파일의 베트남어 항목은 원어민 검수 전 임시값이며, 기획 담당이 확정해 교체합니다(OPEN-03).

## 10. API 명세

REST + JSON, 인증은 세션 쿠키(httpOnly)입니다. 모든 요청은 서버에서 역할과 기관을 확인하고, 권한이 없으면 403, 상태 전환이 맞지 않으면 409를 반환합니다.

| 메서드 · 경로 | 역할 | 요청 | 응답·비고 |
| --- | --- | --- | --- |
| POST /api/auth/login | 전체 | login\_id, password | 사용자 정보, role |
| POST /api/auth/logout | 전체 | — | 204 |
| GET /api/residents | caregiver·reviewer | — | caregiver는 배정 어르신만 |
| POST /api/drafts | caregiver | resident\_id, observed\_at, note\_text | 202 + draft\_id, status=generating. 처리는 비동기 |
| GET /api/drafts/:id | 작성자·reviewer | — | draft + 표시용 복원된 원문·값(P6) |
| POST /api/drafts/:id/retry | 작성자 | — | error → generating |
| POST /api/drafts/:id/answers | 작성자 | field\_key, answer\_text | 해당 칸 재처리 후 갱신된 칸 |
| POST /api/drafts/:id/submit | 작성자 | — | ready·returned → submitted |
| GET /api/review/queue | reviewer | — | submitted 목록(AC4-1 정렬) |
| PATCH /api/drafts/:id/fields/:key | reviewer | value, status | field\_edit 기록, edited\_by\_reviewer=true |
| POST /api/drafts/:id/approve | reviewer | — | needs\_confirmation 남아 있으면 409 |
| POST /api/drafts/:id/return | reviewer | reason(1\~200자) | submitted → returned |
| GET /api/residents/:id/records | reviewer·admin | from, to | approved 목록 |
| GET /api/drafts/:id/pdf | reviewer·admin | — | approved만. PDF 파일 |
| GET /api/drafts?mine=1 | caregiver | status(선택), date(선택) | 본인 초안 목록. ①의 오늘 제출 여부·반려 알림에 사용 |
| POST /api/drafts/:id/notes | 작성자 | note\_text(1\~1,000자) | returned 상태에서만(아니면 409). 추가 메모 저장 후 초안 전체 재생성, 달라진 칸 표시. 처리는 비동기(202) |

- 초안 생성 진행 상황은 GET /api/drafts/:id 를 1초 간격으로 조회(최대 60초, 서버는 50초가 지나면 error로 전환). reviewer가 처음 조회할 때 review\_opened\_at 기록. 웹소켓은 쓰지 않음
- 오류 응답 형식: {"error": {"code": "UNSUPPORTED\_LANG", "message\_ko": "…", "message\_vi": "…"}}
- 오류 코드: UNSUPPORTED\_LANG, PII\_REMAINING, AI\_FAILED, SCHEMA\_INVALID, INVALID\_TRANSITION, FORBIDDEN, NOTE\_EMPTY, NOTE\_TOO\_LONG

## 12. 평가 도구와 테스트 케이스

평가는 스크립트 하나로 자동 실행되고, 같은 데이터로 케어브릿지와 비교 방식을 돌려 숫자를 냅니다. 평가 도구는 QA 담당이 만들고, 결과는 성과보고서에 그대로 쓰입니다.

**데이터 형식** — eval/data/\*.jsonl, 한 줄에 메모 하나

```json
{"id": "dev-0001", "scenario": "meal", "difficulty": "vague", "source": "synthetic", "note": "Bà [R1] ăn trưa được một nửa, uống nước nhiều.", "gold": {"meal_lunch": "1/2", "water_intake": "__CONFIRM__", "stool_count": null}}
```

- gold 값: 정답 값 / null(메모에 없음, missing이 정답) / "**CONFIRM**"(needs\_confirmation이 정답)
- source: synthetic(AI 생성) 또는 human(유학생 작성). human 데이터는 eval/data/test\_human.jsonl에만 두고 프롬프트 개선에 쓰지 않음
- 데이터 내용은 기획·자료 담당이 공급. 구현자는 형식 검사와 실행만 담당

평가 데이터의 note는 P1을 거친 모양(\[R1\] 등)으로 저장하고 P2부터 실행합니다. 가명처리(P1)는 TC-01·TC-02와 '가명처리 누출' 지표로 따로 검증합니다.

### 정답 데이터 작성 기준

평가 수치가 믿을 만하려면 누가 만들어도 같은 정답이 나와야 합니다. 메모와 정답은 아래 규칙으로만 만들고, 규칙에 없는 경우는 기획 담당이 정해 이 절에 추가합니다.

**데이터 묶음**

| 파일 | 용도 | 규모 | 만드는 방법 |
| --- | --- | --- | --- |
| dev.jsonl | 프롬프트·규칙 개선 | 100건 | AI 생성 + 팀 검토 |
| test\_synthetic.jsonl | 중간 평가(개발 중 열어보지 않음) | 20건 | AI 생성 + 팀 검토 |
| test\_human.jsonl | 최종 평가 | 20\~30건 | 유학생이 상황 카드를 보고 직접 작성 |

**시나리오 표** — 상황 8종 × 난이도 5종 = 40칸. dev는 칸마다 2\~3건, test는 칸이 고루 걸치도록 뽑습니다.

| 구분 | 항목 |
| --- | --- |
| 상황(scenario) | meal(식사), water(수분), excretion(배설), position(체위변경·이동), hygiene(세면·목욕), vital(혈압·체온·혈당), mood(인지·정서), incident(이상 상황: 어지러움·낙상 등) |
| 난이도(difficulty) | clear(정보가 분명함), missing(일부 정보 없음), vague(애매어 포함), mixed(베트남어·한국어 혼용, 구어·오타), pii(이름·연락처·호실 포함) |

**메모 작성 규칙**

1. 1\~5문장, 50\~300자. 요양보호사가 일하다가 급하게 쓰는 말투로 쓴다(완성된 문장만 쓰지 않기).
2. 한 메모에 칸 2\~4개분의 정보를 넣는다.
3. 사람 이름은 시드 명단의 가상 이름만 쓴다. 실제 사람·실제 연락처 금지. pii가 아닌 메모는 \[R1\] 토큰 형태로 저장한다.
4. 의학적 진단이나 처치를 지어내지 않는다. 관찰한 사실과 요양보호사가 한 일(보고, 도움)만 쓴다.

**정답(gold) 작성 규칙**

1. 7장 칸 목록의 모든 key에 정답을 적는다. 값, null(메모에 없음), "**CONFIRM**"(확인 필요) 중 하나.
2. 메모에 직접 적힌 것만 값으로 적는다. "점심 반 드심"에서 아침·저녁은 null이다.
3. 수량형 칸의 근거가 애매어(9장 목록)이면 "**CONFIRM**".
4. enum 칸은 허용 변환표대로 바꾸어 적고, 변환표에 없는 표현이면 "**CONFIRM**".
5. text 칸(cognitive\_emotional, special\_notes)은 문장 대신 포함해야 할 사실 목록으로 적는다: {"facts": \["14시경 어지러움 호소", "간호사에게 알림"\]}. 평가는 사실마다 '들어감/빠짐/틀림'을 사람이 판정한다.
6. 숫자는 칸의 단위로 적는다(혈압 "130/80", 체온 37.8). 메모에 단위가 없고 구분이 안 되면 "**CONFIRM**".

**예시**

```json
{"id": "dev-0042", "scenario": "incident", "difficulty": "mixed", "source": "synthetic", "note": "[R1] an trua dc 1 nua, 2h chieu noi chong mat, da bao y ta. huyet ap 150/90", "gold": {"meal_lunch": "1/2", "blood_pressure": "150/90", "special_notes": {"facts": ["14시경 어지러움 호소", "간호사에게 알림"]}, "meal_breakfast": null, "stool_count": null}}
```

(예시의 gold는 일부 key만 보였으며, 실제 파일에는 모든 key를 적습니다. 베트남어 문장은 성조 부호를 빼고 급하게 쓴 모양을 흉내 낸 것이며, 원어민 검수 전 임시 예시입니다.)

**검수 절차**

1. 작성자 1명이 만들고, 다른 팀원 1명이 정답만 보지 않고 따로 적어 비교한다.
2. 두 사람의 정답이 다른 칸은 기획 담당이 결정하고, 필요하면 이 규칙을 고친다.
3. 베트남어 메모의 자연스러움은 원어민이 20\~30%를 표본 검수한다.
4. 각 항목에 review\_status(draft·cross\_checked·native\_checked)를 적고, 수정한 항목은 사유를 별도 변경 기록에 남긴다.

**지표 계산**

| 지표 | 계산 |
| --- | --- |
| 누락률 | gold에 값이 있는 칸 중 출력이 missing인 칸 수 ÷ gold에 값이 있는 칸 수 |
| 지어낸 값 | gold가 null인데 출력이 filled인 칸 수(합계) |
| 값 오류율 | gold에 값이 있고 출력도 filled인 칸 중 값이 다른 칸 비율(enum·숫자는 일치 비교, text는 사람 판정 칸으로 분리) |
| 확인 요청 적중 | gold가 \_\_CONFIRM\_\_인 칸 중 출력도 needs\_confirmation인 비율 |
| 과잉 확인 요청 | gold가 값인데 needs\_confirmation으로 나온 칸 비율(너무 높으면 사용자 피로) |
| 가명처리 누출 | 외부 요청 본문에서 명단 이름·전화번호가 발견된 건수(반드시 0) |
| 담당자 확인 시간 | approved\_at − review\_opened\_at(초). 자동 평가가 아니라 사용자 테스트에서만 측정 |
| 담당자 수정 칸 수 | 초안 1건당 field\_edit 건수. 사용자 테스트에서 측정 |

**비교 방식**: baseline = 같은 모델에 "베트남어 메모를 번역해 기록지 칸을 채워라"만 주는 단순 프롬프트(prompt\_version: baseline-v0), 검사(P4) 없음. 실행: `python eval/run_eval.py --data eval/data/dev.jsonl --pipeline carebridge|baseline` → eval/out/에 칸별 결과 CSV와 요약 표 생성.

**필수 테스트 케이스**

| ID | 대상 | 내용 | 기대 결과 |
| --- | --- | --- | --- |
| TC-01 | P1 | 메모에 "bà Lan"(명단 이름)과 010-1234-5678 | 외부 요청에 \[R1\], \[PHONE\]만 있음 |

## 13. 기술 스택

아래 스택은 기본안이며, 백엔드 담당이 다른 언어에 익숙하면 10/8까지 바꿀 수 있습니다(OPEN-02). 스키마 검증과 AI 호출이 많아 백엔드는 Python을 기본으로 잡았습니다.

| 영역 | 기본안 |

| 프론트엔드 | Next.js(React) + TypeScript, Tailwind CSS, 문구는 locales/ko.json·vi.json |
| 백엔드 | Python FastAPI, Pydantic(7장 스키마 = Pydantic 모델), 비동기 작업은 FastAPI BackgroundTasks |
| DB | 개발 SQLite → 배포 PostgreSQL. ORM은 SQLAlchemy |
| AI | LLM 제공사·모델은 OPEN-04. 호출은 ai\_client.py 하나로 모아 교체 가능하게 |
| PDF | 서버에서 HTML → PDF 변환(WeasyPrint 등) |
| 배포 | 프론트 Vercel, 백엔드·DB는 Render·Railway 등 무료·저가 플랜 |
| 협업 | GitHub 저장소 1개(모노레포), Issue 템플릿, PR당 리뷰어 1명 이상 |

**저장소 구조**

```text
carebridge/

  backend/
    app/api/         # 10장 엔드포인트

    config/          # form_facility_v1.json, number_map.json, vague_terms.json

```
