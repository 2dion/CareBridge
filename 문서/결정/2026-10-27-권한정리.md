# 이력·AI 작업 기록·처리 상태는 서버와 DB만 쓰고, 수정 이력은 DB가 자동으로 남긴다

- **상태:** 유효
- **정한 날·사람:** 2026-10-27 · 백엔드 담당 제안, 2dion(팀장) 승인[3]. QA 10/27 실제 DB 대조 5~10번에 대한 답
- **관련:** 데이터 구조 v1.6.1 '권한 규칙'·record_events·audio_jobs·agent_steps·공통 계약 PATCH 규칙, AGENTS.md 원칙 1·4·5

## 배경

QA가 실제 Supabase의 정책·칸 권한·트리거를 대조해, 브라우저의 공개 키로 DB를 직접 부르면 할 수 있는 일 6가지를 찾았습니다.[1] 화면에는 그런 버튼이 없지만, 돌봄 기록은 공식 기록이라 이력과 근거를 사람이 꾸밀 수 없어야 합니다(원칙 1·5).

| # | 지금 할 수 있는 것 |
| --- | --- |
| 5 | 작성자가 `agent_steps`(AI 작업 기록)를 직접 넣음 |
| 6 | 작성자가 되돌아온 기록의 되돌린 사유를 고침 |
| 7 | 작성자가 `record_events`에 `resolved`·`edited`·`ai_filled`를 직접 넣음 |
| 8a | 작성자가 항목 `source`를 `reviewer`로 바꿈 |
| 8b | 작성자가 `audio_jobs`의 상태·파일 경로를 언제든 바꿈 |
| 9 | 담당자가 보낸 기록의 원문(`transcript`·`transcript_ko`)을 고침 |
| 10 | 항목·원문 수정 이력은 API가 빠뜨리면 남지 않음 |

지금 문서는 "서버도 요청한 사람의 권한으로 DB에 씁니다"라고만 정해서, 5·7·10은 이 문장대로 만든 결과입니다.[2]

## 결정

1. **`agent_steps`:** 화면(로그인 사용자)은 쓰지 않습니다. 서버가 Agent를 돌릴 때 service_role로 넣습니다. (5)
2. **`record_events`:** 화면도 서버도 직접 넣지 않고 DB 트리거만 씁니다. (7·10)
   - 상태 변화(`created`·`submitted`·`returned`·`approved`)는 지금처럼 트리거가 씁니다.
   - 항목이 바뀌면 트리거가 한 줄을 남깁니다. 담당자가 `resolution`을 바꾸면 `resolved`, `source = ai`면 `ai_filled`, 그 밖은 `edited`입니다. before/after에는 바뀐 칸만 넣습니다. 번역(`value_native`)만 바뀌면 남기지 않습니다.
   - 원문·서식 칸·방문 시간이 바뀌면 `edited`(item_key 빈값)를 남깁니다.
3. **되돌린 사유:** `return_reason`·`return_reason_native`는 담당자만 바꿉니다. (6)
4. **항목 `source`:** 작성자는 `reviewer`로 바꿀 수 없습니다. 담당자가 내용을 고치면 DB가 `reviewer`로 채웁니다. (8a)
5. **`audio_jobs`:** 만들기는 지금처럼 작성자 권한으로 하고, 처리 상태·경로 바꾸기는 서버가 service_role로 합니다. (8b)
6. **원문:** `transcript`·`transcript_ko`는 그 기록의 작성자(받아쓰기·[글로 쓰기]를 돌리는 작성자 권한 서버)만 바꿉니다. 담당자는 서식 칸·항목은 고치지만 원문은 고치지 않습니다. (9)
7. 그 밖의 쓰기(항목 채우기·고치기, 상태 바꾸기)는 지금처럼 요청한 사람의 권한으로 합니다.

## 검토한 대안

- **그대로 두기 (화면에 버튼이 없으니 괜찮다):** 바꿀 것이 없지만, 공개 키로 직접 부르면 이력·AI 작업 기록을 꾸밀 수 있어 공식 기록의 근거가 흔들립니다.
- **`resolved`만 담당자로 막고 나머지는 열어 두기:** 변경이 가장 작지만, `edited`·`ai_filled`와 AI 작업 기록은 여전히 꾸밀 수 있고 이력 누락(10)도 남습니다.
- **모든 쓰기를 서버 service_role로:** 가장 단단하지만, RLS가 아니라 서버 코드가 권한을 모두 맡게 되어 원칙 7(기관별 RLS)과 기존 설계를 크게 바꿉니다.

## 사유

이력과 AI 작업 기록은 사람이 고칠 이유가 없는 '기록의 기록'이라 쓰는 곳을 DB와 서버로 좁히고, 수정 이력은 API가 빠뜨려도 남도록 DB가 맡습니다. 나머지 쓰기는 지금 RLS 설계를 그대로 둡니다.

## 영향

- **데이터 구조 v1.6 → v1.6.1:** '권한 규칙' 표·설명, record_events·audio_jobs·agent_steps 설명, 공통 계약 PATCH 규칙. 표·칸·상태 값은 그대로.
- **DB(백엔드 담당):** 마이그레이션 `20261027140000_permissions.sql`.
- **서버(백엔드 담당):** agent-run은 `agent_steps`를, audio는 `audio_jobs` 상태를 service_role로 씁니다. 이력은 API가 쓰지 않습니다.
- **화면(프론트엔드 담당):** 바뀌는 것 없음. R2 이력·AI 작업 기록 읽기는 그대로.
- **테스트(QA 담당):** QA 테스트 계획의 5~10번을 "막혀야 함"으로 둡니다.
