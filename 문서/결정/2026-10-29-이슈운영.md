# 남은 문제는 GitHub 이슈로 모으고, 작은 일만 이슈 없이 바로 PR로 올린다

- **상태:** 유효
- **정한 날·사람:** 2026-10-29 · 2dion(팀장)
- **관련:** AGENTS.md '작업 올리는 방법', `.github/ISSUE_TEMPLATE/`, `.github/labels.yml`

## 배경

10/28까지 기본 기능(화면·서버·DB 연결)을 거의 다 올렸습니다. 이제 남은 일은 QA·FE 점검에서 나온 버그, 팀장 결정이 필요한 질문, 용어 맞추기처럼 여러 담당에 걸친 일입니다.[1] 지금까지 규칙은 "작업은 이슈 없이 브랜치 → PR, 이슈는 버그·질문만"이었습니다.[2] 피드백이 카카오톡·디스코드·검토 문서에 흩어져 누가 무엇을 언제까지 하는지 한곳에서 볼 수 없습니다.

## 결정

1. **남은 문제는 GitHub 이슈로 모읍니다.** 카톡·디스코드에서 나온 문제도 이슈로 옮기고, 대화에는 이슈 링크만 남깁니다.
2. **이슈 먼저 쓰는 경우.** 아래 중 **하나라도** 맞으면 이슈를 먼저 쓰고, 고치는 PR 본문에 `Closes #번호`를 씁니다.
   | # | 기준 | 예 |
   | --- | --- | --- |
   | 1 | 다른 사람이 고쳐야 하는 문제를 내가 찾음 | QA가 찾은 화면 버그, FE가 찾은 API 오류 |
   | 2 | 다른 사람(팀장 포함) 답이나 결정이 있어야 시작함 | 사진 칸 넣을지, 문구 정하기 |
   | 3 | 공통 계약(API·상태 값·표·권한), 기획안 결정표, 원칙을 바꿈 | 칸 추가, 상태 이름 변경 |
   | 4 | 두 담당 이상의 코드나 문서를 고쳐야 함 | 용어 통일, 화면+서버 함께 고침 |
   | 5 | 바로 고치지 못함: 오늘 안에 못 끝내거나 PR 두 개 이상으로 나눠야 함 | 화면 하나 새로 만들기 |
   | 6 | 크기가 큼: 바뀌는 파일이 6개 이상이거나 줄이 200줄 넘게 바뀜(lock·자동 생성 파일 빼고) | 큰 리팩터링 |
   | 7 | 다시 재현해야 원인을 앎 | "가끔 두 번 보내져요" |
3. **이슈 없이 바로 PR.** 위 7개에 **모두** 해당하지 않으면 바로 PR로 올립니다. 예: 오타·링크·숫자 고치기, 내 담당 화면의 문구·색·간격, 테스트 추가, 이미 결정 기록이나 이슈로 정해진 대로 구현, 문서를 코드 상태에 맞추기.
4. **하다가 커지면** 그때 이슈를 쓰고 PR에 `Closes #번호`나 `관련 #번호`를 붙입니다.
5. **이슈 쓰는 법.** 템플릿 4개(버그, 기능·개선, 용어·문서, 질문) 중 하나로 씁니다. 빈 이슈는 막습니다.
6. **라벨.** 이슈마다 담당 라벨 하나 이상과 기한 라벨 하나를 붙입니다. 담당자(Assignee)는 이슈를 맡는 사람이 스스로 지정합니다.
   | 묶음 | 라벨 |
   | --- | --- |
   | 담당 | `BE`, `FE`, `QA`, `기획`, `데이터`, `팀장` |
   | 종류 | `버그`, `기능·개선`, `용어·문서`, `질문` (템플릿이 자동으로 붙임) |
   | 기한 | `10/31 전`(공모전 접수), `11/08 전`(파이널 제출) |
7. **질문 이슈의 답이 결정이면** 답한 내용을 결정 기록이나 문서에 옮기는 PR이 이슈를 닫습니다. 단순 답이면 답한 사람이 닫습니다.
8. **실명 금지는 이슈에도 같습니다.** 저장소가 공개라서 이슈·댓글에도 역할 이름이나 GitHub 아이디만 씁니다.

## 검토한 대안

- **기존 규칙 유지(이슈는 버그·질문만):** 남은 일 대부분이 다른 담당 몫이라 대화에서 잊힙니다.
- **모든 작업을 이슈부터:** 오타 하나에도 이슈를 써야 해서 마감 전 속도가 떨어집니다.
- **GitHub Projects 보드:** 팀이 쓰지 않기로 했고(10/20), 라벨 필터로 충분합니다.

## 사유

다른 사람이 알아야 하거나 기다려야 하는 일만 이슈로 남기면, 이슈 목록이 곧 '남은 일 목록'이 되고 작은 일은 지금 속도를 지킵니다. 파일 6개·200줄은 한 사람이 리뷰 없이 한 번에 읽을 수 있는 크기로 잡았습니다.
