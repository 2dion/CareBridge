# 용어 번역을 언어별 표로 나누고, 기록에 작성 언어를 남긴다 (다국어 확장 단계 2)

- **상태:** 유효
- **정한 날·사람:** 2026-11-03 · 백엔드 담당 (팀장이 이슈 #259로 범위를 정함)
- **관련:** [다국어 확장 구조 v2.0.0](../설계/다국어확장-v2.0.0.md) '목표 구조 2~4'·'단계 2', 결정 [용어표](2026-10-21-용어표.md)(칸 이름 일부 바꿈), 결정 [확인필요이유병기](2026-10-27-확인필요이유병기.md)(번역 표를 언어별 파일로), 데이터 구조 v2.3.0(표 `glossary_translations`, `records.native_lang`, 공통 계약 `search_glossary`·`POST /api/helper/ask`), 이슈 #259, 단계 0 PR #257

## 배경

- 용어표 `glossary`의 번역 칸은 `term_vi` 하나라, 언어를 더할 때마다 칸과 `search_glossary()` 결과 모양을 바꿔야 합니다.[1]
- 코드가 붙이는 '확인 필요' 이유의 번역(`REASONS_VI`)과 AI 프롬프트의 언어 이름("베트남어로 번역한다")이 코드에 박혀 있습니다.[1]
- 작성자가 모국어를 바꾸면 옛 기록의 `value_native`·`reason_native`가 어느 언어인지 알 수 없습니다.[1]
- 단계 0(#257)으로 모국어 값 읽기는 `parseNativeLang` 한곳으로 모았습니다. 이번은 DB와 서버 쪽 구조입니다.

## 결정

1. **새 표 `glossary_translations`:** 용어 1개 × 언어 1개 = 1행(`glossary_id`, `lang`, `term`, `reviewed`). 모든 기관이 함께 읽고(`glossary`와 같은 RLS), 넣기는 시드·SQL만. `lang`은 check 제약 목록이고 언어를 더할 때 마이그레이션으로 고칩니다. 표 16개 → 17개.
2. **`term_vi`는 전환 기간 동안 남김:** 기존 값을 vi 행으로 옮기고, `term_vi`가 바뀌면 트리거가 vi 행을 같은 값으로 맞춥니다(번역 글이 바뀌면 `reviewed`는 내림). 시드(`seed-glossary.sql`)는 그대로 돌릴 수 있습니다. 화면·서버가 모두 `term_native`로 옮긴 뒤 칸과 트리거를 지웁니다(별도 이슈).
3. **`search_glossary(expression, max_results, lang)`:** 결과에 `term_native`(그 언어 번역, 없으면 빈값)를 더합니다. `lang`을 보내지 않으면 `vi`. `term_vi`도 전환 기간에는 함께 줍니다. 번역이 없으면 AI는 교재 용어(한국어)만 쓰고 번역을 짐작하지 않습니다(원칙 2).
4. **`records.native_lang`:** 기록을 만든 때 작성자 언어. DB 트리거가 `profiles.native_lang`에서 채우고(보내온 값은 무시), 만든 뒤에는 서버도 바꾸지 못합니다(`care_date`와 같이 고정). 있던 기록은 지금 작성자 언어로 채웁니다.
5. **코드 이유 번역은 언어별 파일:** `REASONS_VI` → `web/lib/agent/reasons/<lang>.ts`, `REASONS_NATIVE[lang]`. 그 언어 고정문이 없으면 `reason_native`는 빈칸이고 화면은 한국어 이유만 보입니다. 재가 제공 지원 재검사(`support-check`)가 서버 이유를 걷어 낼 때는 모든 언어 고정문을 봅니다.
6. **언어 이름은 언어 목록에서:** `web/lib/i18n/languages.ts`(`code`, `nameKo`, `nameNative`)가 한 곳이고, `NATIVE_LANGS`·`parseNativeLang`도 여기로 옮깁니다(`signup.ts`는 다시 내보냄). 번역·Agent·도우미·항목 보태기 프롬프트는 `nameKo`를 넣습니다.
7. **도우미 답 칸 `vi` → `native`:** `POST /api/helper/ask` 출력은 `native`가 기준이고, 화면이 옮길 때까지 `vi`도 같은 값으로 함께 보냅니다. 모델이 옛 칸 이름으로 답해도 받아 줍니다.
8. **데이터 파일:** 베트남어 번역은 `data/glossary/translations-vi.csv`(`term_id`, `term`, `reviewed`)로 나누고, 시드는 `seed-glossary-translations-vi.sql`(용어는 `expression`·`term_ko`로 찾음)입니다. 원본 `terms-v0.3.csv`의 베트남어 열은 그대로 둡니다(데이터 담당이 다음 판에서 정리).

## 검토한 대안

- **대안 A: `glossary`에 `term_<lang>` 칸을 언어마다 추가:** 마이그레이션이 짧음 / 언어마다 칸·함수·타입을 고쳐야 하고, 검수 여부를 둘 곳이 없음. 버림
- **대안 B: `term_vi`를 바로 지우고 번역 표만 둠:** 구조가 깨끗함 / 시드·화면·테스트가 한 번에 바뀌어야 해서 PR이 커짐. 버림(전환 기간 뒤 별도 이슈로)
- **대안 C: `records.native_lang`을 서버 코드가 넣음:** 트리거가 없음 / 기록을 만드는 길이 둘(화면 insert, 서버)이라 빠뜨리기 쉽고, 화면은 이 칸에 insert 권한이 없음. 버림(DB가 채움)
- **대안 D: 도우미 출력 `vi`를 바로 `native`로 바꿈:** 계약이 단순 / W6 화면이 같은 PR에서 바뀌어야 함(FE 단계 1). 버림(두 칸을 함께 보냄)
- **채택:** 새 표 1개 + 칸 1개 + 함수 인자 1개 + 언어별 파일, 베트남어만 있는 지금 동작은 그대로

## 사유

- 언어를 더하는 일이 '행·파일 추가'가 되어 DB 함수·타입을 다시 고치지 않습니다.
- 번역이 없을 때 빈칸으로 두는 규칙이 DB(`term_native`)·코드(`reason_native`)에서 같아, 다른 언어 번역을 조용히 주는 일이 없습니다(단계 0과 같은 원칙).
