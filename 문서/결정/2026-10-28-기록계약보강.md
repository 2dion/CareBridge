# 이유 번역·검토 상태·제출 검사·작성 출처·프로필 조회를 독립된 권한으로 처리한다

- **상태:** 유효
- **정한 날·사람:** 2026-10-28 · 2dion
- **관련:** 데이터 구조 v1.6.2, AI 규칙 v1.1.1, 화면 v1.3, 백엔드 착수 전 점검

## 배경

이유 번역이 검증 과정에서 빠지고, 화면의 ‘기록 안 함’과 DB 제약이 서로 달랐습니다. DB 제출 검사와 사람 수정 보호를 보강하고, 개인 정보·업무 정보·서버 검사 목록이 서로의 권한을 넓히지 않도록 나눕니다.

## 결정

1. `reason_native`를 검증·저장·사용자 권한 재조회까지 보존합니다. 서버가 이유를 보태면 고정된 한국어 이유와 모국어 문구를 함께 추가합니다. 저장은 `saveValidatedDraft`, 재조회는 `readRecordItems`를 사용합니다.
2. **기록 안 함은 `status = needs_check`, `resolution = omitted`입니다.** 한국어·모국어 내용은 비우며 승인 때는 미처리 `needs_check`만 막습니다. 다시 정하기는 resolution을 비웁니다. ‘언급 없음’은 처음부터 관찰 내용이 없는 항목의 상태이며 생략 결과와 구분합니다.
3. 제출 때 DB도 9개 항목이 모두 있고, 모든 항목이 `confirmed`이거나 `source = worker`인지 검사합니다. 로그인한 작성자의 직접 DB 갱신도 같은 조건을 적용합니다.
4. 사람이 수정한 항목은 내용 변경 없이 source만 `ai`로 돌리는 것도 금지합니다. 사용자는 source·근거·이유·번역을 직접 쓰지 않습니다. DB가 실제 작성자·담당자의 내용 수정에 맞춰 출처를 정하고, 검증된 AI 저장은 서버 전용 RPC로 구분합니다. AI 재실행은 사람이 수정한 항목을 건너뜁니다.
5. 작성자·담당자는 profiles에서 자기 행만 직접 읽습니다. 담당자는 `list_org_staff()`로 같은 기관의 업무 필드 `id/name/role`만 읽습니다. 서버는 `record_blocked_names(record_id, worker_id)`로 검사할 기록의 기관 이름 목록만 읽습니다. 이 RPC는 service_role만 실행할 수 있으며 기록의 작성자·기관·상태를 검사합니다.

## 구현 경계

- 일반 기록 생성·수정·제출·승인과 재조회는 로그인 사용자 RLS로 처리합니다.
- AI 초안 저장 예외는 service_role 전용 `save_record_ai_draft` RPC 하나로 제한합니다. 서버가 검증한 사용자 id와 기록을 전달하며 DB가 작성자·기관·상태·현재 원문을 다시 확인하고, 사람 수정 항목은 갱신하지 않습니다. 범용 관리자 UPDATE로 대체하지 않습니다.
- 서버 전용 모듈에서 인증된 작성자와 원문을 읽고 이름 검사·초안 검증·저장·재조회를 연결합니다. 실제 Agent 실행 API와 화면의 Mock 교체는 후속 작업입니다.
- value_ko를 사람이 고치면 오래된 value_native는 비웁니다. 번역(value_native/reason_native) 변경도 DB가 이력에 남깁니다.
- 전체 화면·서비스 용어 재정리는 별도 후속 작업입니다. 지금의 ‘확인 필요’와 ‘기록 안 함’ 의미를 임의로 합치지 않습니다.

## 검증과 반영

사용자 요청에 따라 추가 수동 검증은 진행하지 않습니다. 중단 전에 별도 PostgreSQL 환경에서 기존 마이그레이션과 합성 트랜잭션 회귀 SQL을 실행했습니다. 이후 수정한 최종 상태는 전체 검사·빌드를 다시 실행하지 않았습니다. 마이그레이션의 클라우드 적용과 실제 서비스 흐름 검증은 후속 반영 단계에서 수행합니다.

## 대안과 사유

- 생략을 not_mentioned로 바꾸는 안은 채택하지 않습니다. 화면의 needs_check와 resolution 조합으로 통일합니다.
- 작성자의 기관 전체 profiles 읽기는 채택하지 않습니다. 서버 이름 검사를 위해 브라우저의 조회 범위를 넓히지 않습니다.
- 클라이언트가 출처를 선언하는 방식은 채택하지 않습니다. 사람의 실제 수정과 서버 AI 저장을 DB에서 구분합니다.
