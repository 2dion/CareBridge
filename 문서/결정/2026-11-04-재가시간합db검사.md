# 재가 지원 시간 합 검사(검사 5)는 전송 때 DB도 한다

- **상태:** 유효
- **정한 날·사람:** 2026-11-04 · 백엔드 담당 (팀장이 이슈 #278로 범위를 정함)
- **관련:** AGENTS.md '바꾸지 않는 원칙' 5번, AI 규칙 v2.0.4 '서버 검사와 예외 처리' 검사 5, 데이터 구조 v2.3.3 공통 계약 `POST /api/records/:id/submit`·'응답 코드와 오류 키', 결정 [초안검사보강](2026-10-29-초안검사보강.md)(검사 5 재검사), 이슈 #278

## 배경

- 11/03 보안 점검(Cloudflare security-audit quick)에서 '확인 낮음' 1건: 작성자가 화면을 거치지 않고 PostgREST로 `records.status`를 `submitted`로 직접 바꾸면 재가(제12호) 지원 시간 합 검사(검사 5)를 건너뜁니다.
- 검사 5는 서버 API(초안 검증, W3 PATCH 뒤 재검사, 전송 직전 재검사)에만 있었고, DB 트리거는 항목 확인(`unconfirmed_items`)만 봤습니다.
- 11/04 코디세이 DB에서 재현: 방문 60분인 재가 기록에 지원별 분 합 150분을 넣고 작성자 권한으로 직접 `submitted`로 바꾸면 그대로 넘어가고, 제공 지원 항목은 '관찰' 그대로였습니다.

## 결정

1. **DB 트리거가 전송 때 검사 5를 다시 합니다.** `private.records_before_update`의 `draft·returned → submitted` 분기에서, 재가 기록의 제공 지원 분 합이 방문 시간보다 크면 `support_minutes_exceed_visit`, 방문 시간을 모르는데 분이 적혀 있으면 `visit_minutes_missing`으로 거절합니다. 규칙(합산하는 6칸, 0 이상 정수만, 방문 시간을 찾는 순서)은 서버 코드와 같습니다.
2. **제공 지원 항목이 이미 '확인 필요'면 통과합니다.** 서버는 전송 직전 재검사로 합이 어긋난 항목을 '확인 필요'로 표시하고 이유를 붙인 뒤 전송하므로(이슈 #116), 화면 전송 흐름은 그대로입니다. '확인 필요'가 남은 기록은 관리자가 M2에서 [확인함]/[기록 안 함]을 고르기 전에는 승인되지 않습니다(원칙 3).
3. **오류 키 2개를 공통 계약에 더합니다.** 서버 API는 DB가 이 키로 거절하면 409로 같은 키를 돌려줍니다. 정상 흐름에서는 서버 재검사가 먼저 돌아 이 응답이 나오지 않고, 재검사가 실패했을 때의 안전망입니다.
4. **보지 않는 것:** 시설(제16호) 기록, 합이 0인 기록. 분 칸의 형식 오류(글자·소수·정해진 칸 밖)는 서버 검사가 '확인 필요'로 표시하고, DB는 그 값을 합에서 뺄 뿐 따로 거절하지 않습니다.

## 검토한 대안

- **대안 A: DB 트리거가 서버처럼 '확인 필요'와 이유를 직접 써 줌:** 화면·직접 전송이 완전히 같아짐 / 이유 문구(한국어·모국어)를 SQL에 한 벌 더 두어야 하고, 항목 트리거의 권한 검사와 얽힘. 버림
- **대안 B: RLS 조건으로 막음:** 트리거 없이 됨 / 거절 이유가 '0행'으로만 나와 서버가 원인을 알 수 없음. 버림
- **채택:** 트리거 거절 + '확인 필요'면 통과

## 사유

- 시간 합 계산과 승인 조건은 코드가 맡는다는 원칙 5를 DB까지 넓혀, 화면을 거치지 않는 요청도 같은 규칙을 받습니다.
- 서버의 정상 흐름('확인 필요' 표시 뒤 전송)을 바꾸지 않아 화면·FE 작업이 없습니다.
