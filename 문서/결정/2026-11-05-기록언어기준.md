# 기록의 번역 언어는 기록을 만든 때 언어(records.native_lang)로 고정하고, 서버 번역 경로도 이를 따른다

- **상태:** 유효
- **정한 날·사람:** 2026-11-05 · 백엔드 담당 (이슈 #336)
- **관련:** 결정 [언어선택화면](2026-11-05-언어선택화면.md) 5번, 결정 [용어번역표](2026-11-03-용어번역표.md) 4번(`records.native_lang`), 결정 [되돌림사유번역](2026-10-28-되돌림사유번역.md), [다국어 확장 구조 v2.0.0](../설계/다국어확장-v2.0.0.md) '목표 구조 2', 이슈 #259·#313·#308

## 배경

- 작성자가 W5에서 모국어를 바꿀 수 있게 되면서(언어선택화면), 기록마다 만든 때 언어(`records.native_lang`)가 고정이고 지금 언어와 다르면 번역 줄을 숨기기로 했습니다(5번).
- 그런데 서버 쪽 네 경로는 **지금 프로필 언어**로 번역을 정하고 있었습니다: 항목 수정 재번역(`item-patch-supabase.ts`), 초안 재생성의 이유 번역(`saveValidatedDraft`, `buildValidateContext`), 재가 제공 지원 재검사(`support-check-supabase.ts`), 되돌림 사유 번역(`return-translation*.ts`).
- 그대로면 vi로 만든 기록을 ko·zh로 바꾼 뒤 고칠 때, 저장된 번역의 실제 언어와 `records.native_lang`이 어긋납니다. 화면은 작성 언어만 보고 표시하므로 번역이 사라지거나 다른 언어가 vi로 표시됩니다.

## 결정

1. **언어 기준은 하나입니다:** 번역·이유 번역·사유 번역을 정하는 언어는 모두 그 기록의 `records.native_lang`입니다. 작성자의 지금 `profiles.native_lang`은 쓰지 않습니다. 새 기록의 `native_lang`은 만들 때 DB가 프로필에서 채우므로(용어번역표 4번) 새 기록의 동작은 그대로입니다.
2. **적용 경로 네 곳:** 항목 수정 재번역, 초안 재생성(에이전트 호출 언어 포함)·검증 이유, 재가 제공 지원 재검사, 되돌림 사유 번역.
3. **한국어로 만든 기록(`ko`)은 번역하지 않습니다.** 값이 비었거나 모르는 언어면 `ko`로 읽어 엉뚱한 언어로 번역을 쓰지 않습니다.
4. **‘열 때 다시 번역’은 쓰지 않습니다.** 다국어 확장 문서의 옛 제안(언어가 다르면 열 때 서버가 다시 번역)을 이 결정이 대체합니다. 지금 언어와 다른 기록은 번역 줄을 숨기고 한국어만 보입니다. 작성자가 원래 언어로 되돌리면 저장된 번역이 그대로 다시 보입니다.
5. **관리자 읽기:** 관리자는 작성자 `profiles`를 읽지 못하지만 같은 기관 `records`는 RLS로 읽으므로, 항목 수정에서 서버 전용 읽기가 필요 없어졌습니다.
6. **바뀌지 않는 것:** API 경로·응답, DB 표·RLS·트리거, 상태 값(공통 계약 변경 없음).

## 검토한 대안

- **대안 A: 지금 프로필 언어로 다시 번역해 덮기(기존):** 항상 지금 언어로 보임 / 기록 언어 메타데이터와 어긋나고 옛 번역이 사라짐. 버림
- **대안 B: 언어가 다르면 열 때 서버가 다시 번역하고 `native_lang`을 바꾸기:** 언어를 바꿔도 번역이 따라옴 / `native_lang`은 DB가 바꾸지 못하게 막아 두었고 토큰이 늘며, 두 언어 번역이 섞임. 버림
- **채택:** 기록 언어 고정, 서버도 같은 기준

## 사유

- 화면(#335)이 이미 ‘기록 언어 ≠ 지금 언어’이면 번역을 숨기고 자동 사유 번역을 생략합니다. 서버도 같은 기준이어야 직접 요청·수정·재생성에서도 저장 번역과 기록 언어가 맞습니다.
- 바꾸는 곳이 서버 읽기 쪽뿐이라 DB 변경·배포가 필요 없습니다.
