# 서버 API의 응답 코드와 오류 키를 공통 계약에 적는다

- **상태:** 유효
- **정한 날·사람:** 2026-10-28 · 백엔드 담당
- **관련:** 데이터 구조 v1.6.2 공통 계약 'API 경로'·'응답 코드와 오류 키', supabase/README.md 오류 키 표, AI 규칙 v1.1.1 '서버 검사와 예외 처리'·멈춤 규칙 4, 녹음업로드 결정 3·4번

## 배경

공통 계약은 "권한이 없으면 403, 지금 상태에서 할 수 없으면 409"와 가입 오류 4개만 정했고 "응답 코드 번호는 첫 안"이라고 남겼습니다. 10/28 서버 API 10개를 모두 만들면서 문서에 없는 경우(로그인 안 함, 입력 형식 오류, 키 없음, 받아쓰기 뒤 처리 중, 같은 녹음 두 번)가 나와 백엔드가 코드와 오류 키를 정했습니다. 화면이 같은 키로 안내 문구를 고르려면 한 곳에 적어야 합니다.

## 결정

1. 오류 응답은 모두 `{ "error": "<키>" }`이고, 더 줄 것이 있으면 칸을 덧붙입니다(예: `items`). 키는 DB 트리거 오류 키(supabase/README.md)와 같은 글자를 씁니다.
2. 코드 규칙: 400 입력 형식, 401 로그인 안 함, 403 권한 없음, 404 볼 수 없는 기록, 409 지금 상태에서 못 함, 415 녹음 형식, 422 받아쓴 글 없음, 502 외부 AI·받아쓰기 실패, 503 키 없음(Mock 모드).
3. 키가 없는 서버(`USE_MOCK_AI`가 `false`가 아님)는 가짜 결과를 만들지 않고 503 `ai_not_configured`로 거절합니다. 실제 DB에 가짜 기록이 들어가지 않게 하기 위해서입니다.
4. `/audio`의 기록 전체(`target = record`)는 받아쓰기까지 끝내고 202 + `status = filling`을 돌려주며, Agent는 응답 뒤에 돕니다. 화면은 `audio_jobs.status`(RLS 읽기)로 끝남·실패를 봅니다.
5. 전체 표는 데이터 구조 v1.6.2 공통 계약 '응답 코드와 오류 키'에 둡니다. 바꾸면 그 표를 먼저 고칩니다.

## 검토한 대안

- 코드마다 결정 기록을 따로 쓰기: 이력이 자세함 / 10개 API에 30개 넘는 키라 읽는 사람이 찾기 어려워 버림.
- 403·409 둘만 쓰고 세부는 `error` 키로만 구분: 문서가 짧음 / 화면이 "로그인하세요"와 "권한 없음"을 가르려면 코드가 달라야 해서 버림.

## 사유

화면·서버·QA가 같은 코드와 키를 보고 안내 문구와 테스트를 만들 수 있게, 이미 구현한 값을 한 표로 적습니다. 표·칸·상태 값·API 수는 바뀌지 않습니다.

## 영향

- **공통 계약:** 데이터 구조 v1.6.2에 '응답 코드와 오류 키' 절 추가(버전 유지). "응답 코드 번호는 첫 안"을 이 절로 바꿈.
- **서버(BE):** 바뀌는 코드 없음(이미 이대로 동작).
- **화면(FE):** 오류 키로 안내 문구를 고릅니다. 503 `ai_not_configured`는 "AI 연결 설정이 아직 없습니다"로.
- **테스트(QA):** 테스트 계획의 기대 응답을 이 표로 맞춥니다.
- **운영(팀장):** 정리 작업 비밀 값 `CRON_SECRET`을 Vercel·GitHub Secrets에 둠(10/28 완료).
