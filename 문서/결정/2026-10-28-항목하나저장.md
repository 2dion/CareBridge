# 항목 하나의 재번역과 AI 항목 보태기는 서버 전용 save_ai_item으로 저장한다

- **상태:** 유효
- **정한 날·사람:** 2026-10-28 · 2dion
- **관련:** 기록계약보강 결정 4번, 데이터 구조 v1.6.2 '재번역과 확인 풀림'·공통 계약 PATCH, 되돌림재확인 결정

## 배경

10/28 기록계약보강으로 로그인 사용자는 `value_native`·`reason_native`·`evidence`·`reason`·`source`를 직접 쓰지 못합니다. 서버가 AI 결과를 넣는 길은 9개 전체를 저장하는 `save_record_ai_draft` 하나뿐이었습니다. 그래서 ① 사람이 `value_ko`를 고친 뒤 서버가 다시 번역한 `value_native`, ② W3에서 작성자가 음성으로 항목 하나를 보탠 뒤 Agent가 다시 쓴 항목을 저장할 길이 없어 BE의 PATCH 작업이 막혔습니다.

## 결정

1. 서버 전용(service_role만 실행) DB 함수 `save_ai_item(p_record_id, p_item_key, p_actor_id, p_expected_value_ko, p_mode, p_item)`를 둡니다. 서버는 `p_actor_id`를 로그인 확인(`auth.getUser()`)으로 얻어 넘깁니다.
2. **`p_mode = 'translation'` (재번역):** `value_native`만 바꿉니다. 출처(`source`)와 다른 칸은 그대로입니다. 부를 수 있는 사람은 PATCH와 같습니다. draft·returned면 그 기록의 작성자, submitted면 같은 기관 담당자·강사입니다. `value_ko`가 빈 항목은 거절합니다.
3. **`p_mode = 'item'` (항목 보태기):** `value_ko`·`value_native`·`status`·`evidence`·`reason`·`reason_native`·`detail`을 바꿉니다. 작성자 본인이 draft·returned일 때만 됩니다. 음성 보태기는 작성자의 수정이므로 `source = worker`, `confirmed = false`(다시 [맞아요])입니다. returned면 기존 트리거가 그 항목의 `resolution`과 사유를 비웁니다(되돌림재확인).
4. 두 경우 모두 `p_expected_value_ko`(번역·보태기의 기준 글)가 지금 `value_ko`와 다르면 `stale_item`으로 거절합니다. 그사이 사람이 또 고쳤다는 뜻이므로 서버는 새 글로 다시 합니다. 옛 번역이 새 글을 덮지 않습니다.
5. 이력은 기존 트리거가 남깁니다. 승인된 기록은 `record_locked`입니다.

## 검토한 대안

- `value_native`·`reason_native` 쓰기를 로그인 사용자에게 다시 열기: 가장 빠름 / 사용자가 번역을 꾸밀 수 있어 기록계약보강 4번과 어긋나 버림.
- service_role로 `record_items`를 직접 UPDATE: 코드가 단순 / 작성자·상태·기준 글 검사를 매번 API가 해야 하고 빠뜨리기 쉬워 버림(기록계약보강 '범용 관리자 UPDATE로 대체하지 않음').
- 재번역 함수와 보태기 함수를 따로 두기: 함수마다 단순 / 기관·기록·기준 글 검사가 같아 하나로 합침.

## 영향

- **DB:** 마이그레이션 `20261028130000_save_ai_item.sql`, 회귀 SQL `supabase/tests/save-ai-item.sql`.
- **서버 코드:** `web/lib/agent/draft-repository.ts`의 `saveItemTranslation`·`saveAddedItem`.
- **BE:** PATCH는 ① 사용자 권한으로 `value_ko` 등 저장(트리거가 옛 번역을 비움) → ② 서버가 번역 → ③ `saveItemTranslation`. `stale_item`이면 새 글로 다시 번역합니다.
