# 녹음은 1회용 업로드 주소로 Storage에 바로 올리고, 서버에는 storage_path만 보냄

- **상태:** 유효
- **정한 날·사람:** 2026-10-21 · 백엔드 담당 제안, 2dion 승인
- **관련:** 공통 계약 `POST /api/records/:id/audio`, 데이터 구조 audio_jobs·권한 규칙, [1회 녹음 최대 5분](2026-10-19-녹음5분.md), 기술검토 v1.5 3장 #1·#2

## 배경

v1.1 공통 계약의 `POST /api/records/:id/audio`는 입력이 "음성 파일"이라, 화면이 녹음 파일을 Next.js 서버(Vercel)로 직접 보냅니다. Vercel 함수는 요청 본문이 4.5MB를 넘으면 받지 않아 긴 녹음이 실패할 수 있습니다.[1][2] 기술검토 v1.5는 이것을 공통 계약 확인 전에 고칠 1순위로 짚었습니다.[2]

## 결정

1. **버킷:** Supabase Storage에 비공개 버킷 `audio`를 둡니다. 파일 하나 최대 10MB, 형식은 `audio/webm`(안드로이드·크롬), `audio/mp4`(아이폰 사파리)만 받습니다. 크롬은 `audio/webm;codecs=opus`처럼 뒤에 붙여 만들므로, 화면은 올릴 때 contentType을 `audio/webm` 또는 `audio/mp4`로 맞춰 보냅니다.
2. **경로:** `{org_id}/{record_id}/{uuid}.{webm|mp4}`. uuid와 경로는 서버가 정하고, 화면이 고르지 않습니다.
3. **올리는 순서**
   1. 화면 → `POST /api/records/:id/audio/upload-url` (target, item_key, mime_type)
   2. 서버가 기록 상태(draft·returned)와 작성자를 확인하고, 1회용 업로드 주소(signed upload URL)와 `storage_path`를 돌려줍니다. 주소는 2시간 동안 쓸 수 있고, 같은 경로에 한 번만 올라갑니다.
   3. 화면이 그 주소로 녹음 파일을 Storage에 바로 올립니다. Vercel을 거치지 않습니다.
   4. 화면 → `POST /api/records/:id/audio` (storage_path, target, item_key). 서버는 경로가 이 기록의 경로인지 확인하고 audio_jobs 한 줄(status = uploaded)을 만든 뒤, **같은 요청 안에서** 받아쓰기(Groq STT)를 하고 파일을 지웁니다. 응답 뒤에 따로 돌리면 작성자 로그인 토큰이 만료될 수 있어서입니다(5분 녹음은 수 초).
4. **삭제:** 받아쓰기가 성공하든 실패하든 끝나면 서버가 Storage API로 파일을 지우고 `audio_jobs.storage_path`를 비웁니다. 남은 파일(예: 올리고 audio API를 부르지 않은 것)은 1시간 넘은 것을 지우는 주기 정리를 따로 둡니다. 이 정리는 **Storage API로** 지웁니다. SQL로 `storage.objects` 줄을 지우면 실제 파일은 남기 때문입니다.[3] 실행 방법(Vercel Cron 또는 GitHub Actions)은 구현 때 백엔드 담당이 정합니다.
5. **5분 넘는 녹음 (녹음5분 결정의 서버 쪽):** 화면이 5분에 자동으로 멈추므로, 서버는 길이를 다시 재지 않고 **10MB를 넘거나 형식이 다른 파일은 받지 않습니다**(앞 5분만 잘라 쓰지 않음). 5분 녹음은 보통 webm 약 2~3MB, mp4 약 3~5MB라 10MB 안에 들어갑니다.
6. **권한:** 서버는 service_role 키 없이 로그인한 작성자의 권한으로 업로드 주소를 만들고 파일을 읽고 지웁니다. 그래서 `audio` 버킷에도 RLS를 겁니다: 작성자는 자기 기록(draft·returned) 경로에만 올리고 읽고 지울 수 있고, 담당자·강사는 녹음 파일에 접근하지 않습니다. **예외:** 4번의 주기 정리는 로그인한 사람 없이 돌므로 service_role을 씁니다. 이 키는 서버 환경 변수에만 둡니다.

## 검토한 대안

- 지금 계약대로 서버로 파일을 직접 보냄: 가장 단순하지만, 4.5MB를 넘는 녹음이 Vercel에서 거절됨.
- 1분마다 나눠 보냄(기술 선택 v1.0): 크기 문제는 피하지만 화면·서버 코드가 복잡해지고, 5분 상한이 생긴 뒤로는 필요 없음.
- 화면이 Supabase에 직접 올리고 경로도 화면이 정함: 코드는 줄지만 경로를 화면이 고르면 다른 기록 경로에 올리는 실수를 서버가 막기 어려움.
- 주기 정리를 Supabase pg_cron(SQL)으로: 설정은 쉽지만 실제 파일이 지워지지 않음.

## 사유

Vercel 4.5MB 제한을 구조로 피하면서, 경로와 상태 확인은 서버가 맡고 Storage RLS가 한 번 더 막기 때문입니다. 음성은 받아쓰기가 끝나면 바로 지워 "글자로 바뀌면 삭제" 약속을 지킵니다.[4]

## 영향

- **공통 계약:** `POST /api/records/:id/audio/upload-url`을 더하고, `POST /api/records/:id/audio`의 입력을 "음성 파일"에서 `storage_path, target, item_key`로 바꿉니다(데이터 구조 v1.2, 이 PR).
- **DB(백엔드 담당):** 마이그레이션에서 `audio` 버킷(10MB, 형식 2개)과 Storage RLS를 만듭니다.
- **화면(프론트엔드 담당):** W2(음성 메모)에서 업로드 주소를 받아 Storage에 올린 뒤 audio API를 부릅니다. 크기·형식 오류는 **Storage 업로드 단계**에서 나므로 그 응답을 보고 안내 문구를 띄웁니다. 우리 API의 415는 upload-url에 형식이 틀린 mime_type을 보낼 때만 납니다.
- **문서:** 기술 선택 v1.1 '음성 기록 처리 흐름' 2단계와 위험 표의 '긴 녹음은 나눠 처리'를 이 결정에 맞춰 고칩니다(이 PR).
- **테스트(QA 담당):** 5분 녹음(아이폰·안드로이드)이 올라가고 처리 후 파일이 지워지는지, 다른 작성자의 기록 경로에는 올라가지 않는지, 10MB 넘는 파일이 거절되는지 확인합니다.
