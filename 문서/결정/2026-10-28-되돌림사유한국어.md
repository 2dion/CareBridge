# 되돌리기 API는 한국어 사유만 저장하고, 모국어 번역은 작성자 화면 쪽에서 한다

- **상태:** 대체됨 (2026-10-28, [2026-10-28-되돌림사유번역.md](2026-10-28-되돌림사유번역.md))
- **정한 날·사람:** 2026-10-28 · 백엔드 담당
- **관련:** 데이터 구조 v1.6.2 공통 계약 `POST /api/records/:id/return`·'되돌림·번역', 화면 설계 v1.3 R2 '되돌림 사유', AI 규칙 v1.1.1 ④ 짧은 번역, 피그마상충점 결정 2번(되돌림 부분), 기록계약보강 결정(프로필 조회 분리)

## 배경

공통 계약은 되돌리기 API가 사유를 작성자 모국어로 번역해 `return_reason_native`에 저장한다고 정했습니다.[1] 그런데 번역하려면 작성자의 언어(`profiles.native_lang`)를 알아야 하는데, 10/28 결정으로 담당자는 작성자의 profiles를 읽을 수 없습니다.[2] 담당자 권한으로 도는 API는 작성자 언어를 알 수 없습니다.

## 결정

1. `POST /api/records/:id/return`은 담당자가 쓴 한국어 사유(`reason`)만 `return_reason`에 저장합니다. 담당자는 무조건 한국어로 보냅니다.
2. API는 번역하지 않습니다. 지난 되돌림의 번역이 남지 않게 `return_reason_native`는 빈칸으로 둡니다.
3. 응답은 `status = returned`, `return_reason`입니다.
4. 사유를 작성자 모국어로 바꾸는 일은 작성자 화면 쪽에서 합니다. 구체적인 방법(언제, 어느 경로로 번역하는지)은 확인 필요입니다.

## 검토한 대안

- **서버가 service_role로 작성자 언어 한 칸만 읽어 번역:** 계약을 바꾸지 않음 / 담당자 요청에서 관리자 권한으로 작성자 개인 설정을 읽게 되어 버림.
- **담당자에게 같은 기관 작성자 언어만 주는 DB 함수 추가:** 관리자 권한이 필요 없음 / 마이그레이션이 늘고 프로필 조회 분리 결정을 다시 열어야 해서 버림.

## 사유

담당자 쪽은 한국어 공식 기록만 다루고, 작성자를 돕는 모국어 표시는 작성자 쪽에서 맡아 권한 규칙(프로필 조회 분리)을 그대로 지킵니다.

## 영향

- **공통 계약:** `/return` 출력이 `return_reason_native`에서 `return_reason`으로 바뀝니다. '되돌림·번역'에서 되돌린 사유 번역 문장을 고칩니다. API 수는 그대로입니다.
- **화면 설계 v1.3 R2:** '되돌림 사유'의 'API가 번역해 채움' 문장을 고칩니다. 작성자에게 번역이 보여야 하는 것(W3·W4)은 그대로입니다.
- **AI 규칙 v1.1.1:** ④ 짧은 번역의 '되돌린 사유'는 작성자 화면 쪽 번역으로 옮깁니다.
- **DB:** 바뀌는 것 없음. `return_reason_native`는 담당자만 쓸 수 있어(권한정리 결정), 작성자 쪽 번역은 이 칸에 저장할 수 없습니다. 저장이 필요하면 따로 정합니다.
- **서버(BE):** `web/lib/records/transition.ts` `returnRecord`.
- **화면(FE):** W3·W4에서 `return_reason_native`가 비어 있으면 작성자 쪽 번역을 보여 줄 방법이 필요합니다(확인 필요).
