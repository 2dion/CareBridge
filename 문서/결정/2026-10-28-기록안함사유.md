# [기록 안 함] 사유는 record_items.resolution_note 칸에 저장한다

- **상태:** 유효
- **정한 날·사람:** 2026-10-28 · 2dion
- **관련:** 데이터 구조 v1.6.2 record_items·공통 계약 PATCH, 기록계약보강 결정 2번, 권한정리 결정(이력은 DB 트리거만)

## 배경

데이터 구조는 ‘[기록 안 함] 사유는 이력에 남긴다’고 적었지만 사유를 담을 칸이 없었습니다. 10/27 권한정리로 사용자는 `record_events`에 직접 쓰지 못하고, 이력 트리거는 `record_items`의 칸 변화만 남깁니다. 그래서 화면 Mock의 `resolution_note`는 실제 DB로 바꾸면 사라집니다(10/28 PR #70 검증).

## 결정

1. `record_items`에 `resolution_note`(text, 기본값 빈칸) 칸 1개를 더합니다. 이름은 화면 Mock과 같습니다.
2. 담당자·강사가 [기록 안 함](`resolution = omitted`)을 고를 때 사유를 함께 보냅니다. DB가 앞뒤 공백을 지우고, 비어 있으면 `note_required`로 거절합니다.
3. 사유는 `omitted`일 때만 있습니다. [확인함]·다시 정하기(`resolution` 비움)·되돌린 뒤 작성자 수정으로 `resolution`이 바뀌면 DB가 사유도 비웁니다.
4. 사유를 쓰거나 고치는 것은 담당자·강사만 합니다. 작성자가 바꾸면 `reviewer_only`로 거절합니다.
5. 이력 트리거가 `resolution_note`도 before/after에 넣으므로 `resolved` 줄에 사유가 남습니다. API가 이력을 따로 쓰지 않습니다.
6. 사유는 담당자 화면(R2·R3)에만 보입니다. 작성자에게 보여 줄 번역 칸은 두지 않습니다(병기 원칙 ②의 대상 아님).

## 검토한 대안

- 이력(`record_events`)에 API가 직접 쓰기: 칸이 늘지 않음 / 10/27에 사용자 직접 쓰기를 막았고, service_role로 쓰면 꾸민 이력과 구분이 어려워 버림.
- 사유를 `reason` 칸에 덧붙이기: 칸이 늘지 않음 / `reason`은 AI·서버가 쓰는 ‘확인 필요’ 이유라 섞이면 근거가 흐려져 버림.

## 사유

칸 하나를 더하면 기존 이력 트리거가 그대로 사유를 남기고, 권한 규칙(이력은 DB만 씀)을 바꾸지 않습니다.

## 영향

- **DB:** 마이그레이션 `20261028120000_resolution_note.sql`, 회귀 SQL `supabase/tests/resolution-note.sql`.
- **공통 계약:** PATCH 입력의 ‘resolution + 사유’가 `resolution_note`입니다. 응답 항목에 `resolution_note`를 포함합니다.
- **FE:** R2 [기록 안 함] 사유 입력을 실제 DB로 바꿀 때 `resolution_note`로 보냅니다. Mock은 이미 같은 이름입니다.
