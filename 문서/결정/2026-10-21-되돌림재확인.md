# 되돌린 기록에서 작성자가 고친 항목은 담당자가 다시 확인

- **상태:** 유효
- **정한 날·사람:** 2026-10-21 · 2dion
- **관련:** [승인차단](2026-10-18-승인차단.md)(기획안 결정 8), 데이터 구조 v1.2 record_items.resolution·'PATCH 규칙'·'승인 서버 검사'

## 배경

승인 서버 검사는 "status = needs_check 이고 resolution이 빈 항목이 0개"인지만 봅니다.[1] 담당자가 [확인함]을 고른 뒤 기록을 되돌리고, 작성자가 그 항목을 고쳐 다시 보내면 이전 resolution이 그대로 남아, 바뀐 내용이 담당자 확인 없이 승인될 수 있습니다. 데이터 구조 v1.2에 '확인 필요'로 남아 있던 빈틈입니다.[1]

## 결정

- 기록이 returned일 때 작성자가 항목의 value_ko, status, detail 중 하나라도 바꾸면, 서버가 그 항목의 resolution을 빈값으로 되돌립니다.
- 음성으로 항목을 보태 AI가 그 항목을 바꾼 경우도 '고침'으로 보고 같이 비웁니다.
- 작성자가 고치지 않은 항목의 resolution은 그대로 둡니다.
- 비운 일은 record_events의 `edited` 줄에 resolution 전후 값으로 남깁니다.
- 그래서 다시 보낸 기록에서 고친 항목이 '확인 필요'이면 담당자가 [확인함] 또는 [기록 안 함]을 다시 골라야 승인됩니다. [기록 안 함]으로 비웠던 항목에 작성자가 내용을 다시 넣은 경우도 같습니다.

## 검토한 대안

- 되돌릴 때 모든 항목의 resolution을 비움: 가장 단순하지만, 바뀌지 않은 항목까지 담당자가 다시 눌러야 함.
- 그대로 두고 한계로 적음: 코드는 그대로지만, 확인하지 않은 내용이 승인되는 길이 남아 승인차단 결정과 어긋남.
- 고친 항목만 비움: 담당자 일은 바뀐 항목만큼만 늘고, 승인차단의 취지를 지킴.

## 사유

"작성자가 아닌 사람이 고치면 confirmed가 풀린다"는 기존 규칙과 짝이 맞습니다.[1] 사람이 확인한 내용과 승인되는 내용이 항상 같게 하려는 승인차단 결정의 취지를 지키면서, 담당자에게 다시 맡기는 일은 가장 적습니다.[2]

## 영향

- **데이터 구조 v1.2:** resolution 설명, '[확인함] / [기록 안 함]을 누르면'의 '확인 필요' 줄, 'PATCH 규칙'을 고칩니다(이 PR).
- **서버(백엔드 담당):** PATCH /api/records/:id/items/:key와 항목 보태기(audio, target = item)에서 기록이 returned이면 resolution을 비우는 코드. DB 트리거로 한 번 더 막아도 됩니다.
- **화면(프론트엔드 담당):** R2(검토 화면)에서 다시 보낸 기록이면 resolution이 비워진 항목에 '작성자가 고침' 표시가 있으면 좋습니다(선택).
- **테스트(QA 담당):** [확인함] → 되돌리기 → 작성자가 그 항목 고침 → 다시 보냄 → [승인]이 거절되는지, 고치지 않은 항목은 그대로 [확인함]인지.
