# 계정은 Supabase 이메일 로그인 하나로, 가입은 기관 가입 코드로

- **상태:** 유효
- **정한 날·사람:** 2026-10-25 · 2dion (계정 방식, 가입 코드 방식 모두)
- **관련:** 데이터 구조 v1.3 '표별 칸'(profiles, join_codes)·'권한 규칙'·'공통 계약 API 경로', 화면 설계 v1.1 A1(로그인)·A2(회원가입)·R4(어르신·작성자, 설정), 기술 선택 v1.1 §3

## 배경

FE(프론트엔드 담당)가 로그인·회원가입 화면을 요청했습니다. 지금 화면은 상단 전환 버튼으로 작성자·담당자를 바꾸고, 실제 로그인은 없습니다.[1] DB는 계정마다 기관(`org_id`)과 역할(`role`)이 꼭 있어야 RLS가 동작하는데, 화면에서 profiles를 만들 권한도 API도 없습니다.[2][3] 그래서 가입한 사람의 기관·역할을 어디서 정할지 먼저 정해야 합니다.

## 결정

1. **계정 방식:** Supabase Auth의 이메일·비밀번호 하나만 씁니다. 소셜 로그인, 전화번호, 매직 링크는 쓰지 않습니다(2dion 10/25).
2. **가입 방식:** 기관이 나눠 준 **가입 코드**로 가입합니다. 코드가 기관과 역할을 정하고, 가입한 사람은 고를 수 없습니다.
   - `join_codes` 표(org_id, role, code, active)를 더합니다. 표 12개 → 13개.
   - `POST /api/auth/signup`(코드·이메일·비밀번호·이름·모국어 → 계정)을 더합니다. API 10개 → 11개.
   - 회원가입은 단계를 나누지 않고 한 화면에서 모든 칸을 채워 한 번에 보냅니다. 코드만 먼저 확인하는 API는 두지 않습니다(FE 부담을 줄임, 2dion 10/25).
   - signup은 서버가 service_role로 Supabase 계정을 '이메일 확인됨'으로 만들고 profiles 1행을 함께 넣습니다. 확인 메일을 보내지 않습니다.
3. **Supabase 설정:** Authentication → Providers에서 Email만 켭니다. 'Allow new users to sign up'은 끕니다(브라우저에서 `signUp`을 바로 불러 profiles 없는 계정이 생기는 것을 막음). 비밀번호 최소 8자, 유출 비밀번호 막기를 켭니다.
4. **로그인·로그아웃:** API를 새로 두지 않고 Supabase 클라이언트(`signInWithPassword`, `signOut`)를 씁니다. 세션은 쿠키에 둡니다.
5. **비밀번호 찾기:** MVP에서는 메일을 보내지 않습니다. 화면은 "담당자에게 요청하세요"만 보이고, 팀장이 대시보드에서 비밀번호를 다시 정합니다.
6. **코드 관리:** 코드 값은 팀장이 SQL Editor에서 넣고 저장소에 두지 않습니다(저장소가 공개). 담당자는 R4(어르신·작성자, 설정)에서 자기 기관 코드를 읽기만 합니다.

## 검토한 대안

- **담당자가 R4에서 이메일로 초대:** 담당자가 누구를 들일지 직접 고르는 점은 좋지만, Supabase 기본 메일은 프로젝트 팀원 주소에만 보내고 시간당 보내는 수가 적어 외부 메일(SMTP) 설정 없이는 시연할 수 없습니다.[4] 10/23 기능 마감 뒤라 외부 서비스를 더 붙이지 않습니다.
- **가입 화면 없이 대시보드에서만 계정 만들기:** 공통 계약이 거의 안 바뀌지만, FE가 요청한 회원가입 화면이 없고 교육원에서 교육생이 스스로 계정을 만들 수 없습니다.
- **가입할 때 기관·역할을 목록에서 고르기:** 가장 쉽지만, 아무나 다른 기관의 담당자로 들어가 기록을 볼 수 있어 기관 분리(AGENTS.md 원칙 7)가 깨집니다.
- **Supabase `signUp` + DB 트리거로 profiles 만들기:** API가 줄지만, 코드가 틀릴 때 화면이 받는 오류가 'Database error'로 뭉개져 안내를 할 수 없고, 직접 가입을 켜 두어야 합니다.

## 사유

메일 없이 시연이 되고, 기관·역할을 코드가 정해서 기관 분리가 화면이 아니라 서버에서 지켜지기 때문입니다. 교육용 기관도 교육생용 코드 하나로 같은 흐름을 씁니다.

## 영향

- **데이터 구조:** v1.2 → v1.3(join_codes, API 1개, 권한 규칙, 상태 값). v1.2는 `문서/보관/설계/`로.
- **화면 설계 v1.1:** A1(로그인), A2(회원가입) 추가, W5(내 정보)·R4(어르신·작성자, 설정)에 로그아웃·가입 코드 보기.
- **DB(백엔드 담당):** 마이그레이션에 join_codes 표와 RLS(같은 기관 담당자 읽기만), Supabase 직접 가입 끄기. 서버 환경 변수에 `SUPABASE_SERVICE_ROLE_KEY`(이미 녹음 정리에 쓰기로 함).
- **서버(백엔드 담당):** `/api/auth/signup`.
- **화면(프론트엔드 담당):** A1·A2, 로그인 안 한 사람을 A1로 보내기, 상단 역할 전환 버튼 빼기(Supabase 설정이 없는 개발 환경에서만 남김).
- **테스트(QA 담당):** 틀린 코드, 꺼진 코드, 이미 있는 이메일, 다른 기관 기록 안 보임, 작성자가 R 화면 못 염.
- **일정:** 10/23 기능 마감 뒤 추가입니다. FE→BE 인계(10/26) 범위에 넣을지 팀장이 정합니다.
